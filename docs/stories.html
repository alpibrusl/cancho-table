Thirteen stories, from an order export to the lab.

Lucía sells ceramics online and asks her order file one question after another; each asks a little more of table than the last. Then four short ones from the sciences and two from marketing. Every number and every figure is drawn from a real run of table on the data you can download. The data are invented; the runs are real, and the narration is checked against the numbers whenever the page is generated.

1 · What is in the file?

start heretable

“I sell ceramics online. The shop exports every order as a CSV. Before I ask anything, what did it give me?” — Lucía

With no flags, table only reads the file: how many columns and rows, and what the header is. Nothing is guessed about types; every column is text until you say otherwise. The same call selects columns and prints CSV that another program can read, and a comma inside a quoted field stays inside it.

a real run
$ table  orders.csv
{
  "headers": [
    "order_id",
    "customer_id",
    "date",
    "item",
    "qty",
    "price",
    "status",
    "note"
  ],
  "column_count": 8,
  "row_count": 240,
  "truncated": false
}
a real run
$ table --select order_id,note --limit 4 --format csv orders.csv
order_id,note
1,leave at door
2,
3,leave at door
4,
Reading it. 240 orders, 8 columns. The first rows above are what the file holds; the notes with a comma (“gift, wrap please”) are one cell each, not two. The rest of the page is questions asked of this one file, each a little harder than the one before.

2 · One question, exactly

a filter and a group--where--group--agg--sort

“Which of the pieces that sell for twenty euros or more earned the most from orders that were actually paid?”

One plan, read left to right: keep the paid orders priced at 20.00 or more, group by item, count them and add their prices, sort by that sum. price:dec(2) says the column holds exact decimals with two fractional digits; a bare status = paid compares bytes.

a real run
$ table --where 'status = paid and price:dec(2) >= 20.00' --group item --agg \
    'count,sum:price:dec(2)' --sort -sum:price --format csv orders.csv
item,count,sum:price
vase,35,1567.01
cup set,44,1196.80
teapot,32,1020.80
Reading it. vase leads with 1567.01 euros from 35 paid orders. The numbers are the sums of exact decimals, checked here against a recount of the file in Python’s decimal when the page is generated.

3 · Why decimals? A million tenths

exact arithmeticsum:COL:dec(S)sum:COL:float

“My spreadsheet says the total is a few millionths off. It cannot be, these are euros and cents.”

A double cannot hold a tenth, so a program that adds tenths as doubles accumulates the error. table lets you choose: :dec(S) is an exact decimal with S fractional digits (a cell with more digits is refused, never rounded), :float is the nearest double. A file of one million cells, each 0.1 (generated by this page’s script), summed both ways, and the loop a script would write:

a real run
$ table --agg 'sum:x:dec(1)' million.csv
{"ok":true,"command":"table","schema":"table.v2","data":{"columns":["sum:x"],"rows":[["100000.0"]],"row_count":1,"truncated":false,"next":null,"group_count":1},"meta":{"version":"0.3.0"}}
a real run
$ table --agg sum:x:float million.csv
{"ok":true,"command":"table","schema":"table.v2","data":{"columns":["sum:x"],"rows":[["100000.0"]],"row_count":1,"truncated":false,"next":null,"group_count":1},"meta":{"version":"0.3.0"}}

And the real column: the price of every order, added exactly.

a real run
$ table --agg 'sum:price:dec(2)' orders.csv
[["5901.95"]]
Reading it. A million tenths is 100000.0. The decimal sum says so exactly; the float sum of table also gives 100000.0 here, and the loop of a million additions of 0.1 in doubles gives 100000.00000133288: the error is 1.3e-06, and it grows with the number of rows. (A float sum is still a double, so nothing promises that it is exact in general; a declared :dec is the way to add money.) The sum of the 240 prices of the orders is 5901.95 euros, exact, with no rounding step anywhere.

4 · A refusal that tells you what to type

errors as dataselect.unknown-columnvalue.decimal-scale

“I asked for the wrong column. And then I declared the price with one decimal. What happens?”

A wrong request is not guessed at. table exits with a code, prints one JSON line naming the rule that was broken, a hint in a sentence and a repair: the corrected command as arguments, ready to run. First the misspelt column:

a real run
$ table --where 'status = paid' --select Item orders.csv
exit 3
{
  "code": "NOT_FOUND",
  "rule": "select.unknown-column",
  "message": "--select names a column the header does not have",
  "hint": "pick from detail.available",
  "repair": {
    "kind": "choose",
    "options": [
      {
        "argv": [
          "table",
          "--where",
          "status = paid",
          "--select",
          "item",
          "orders.csv"
        ]
      }
    ]
  }
}
a real run
$ table --where 'status = paid' --select item --limit 3 --format csv orders.csv
item
vase
bowl
teapot

Then a price declared with too few decimals: the data have two, and a decimal is never rounded to fit.

a real run
$ table --where 'price:dec(1) >= 20' orders.csv
exit 8
{
  "code": "PRECONDITION_FAILED",
  "rule": "value.decimal-scale",
  "message": "a cell of a :dec column has more fractional digits than the scale; a decimal is never rounded",
  "hint": "declare a larger scale, :dec(N) with N the most fractional digits the column holds",
  "repair": {
    "kind": "choose",
    "options": [{"argv": ["table", "--where", "price:dec(2) >= 20", "orders.csv"]}]
  }
}
a real run
$ table --where 'price:dec(2) >= 20' --limit 2 --format csv orders.csv
order_id,customer_id,date,item,qty,price,status,note
1,15,2026-02-19,vase,2,44.90,paid,leave at door
3,7,2026-06-18,teapot,3,32.00,paid,leave at door
Reading it. Both refusals have a stable rule (select.unknown-column, value.decimal-scale) that a program can match on, and each carries its own fix: the corrected command, which is the one that was then run. The second repair is the same plan with :dec(2), the most digits the column holds. A person reads the hint; an agent runs the repair.

5 · By month

dates as keys--group date:date@month

“How did the months compare?”

A column read as :date can be a group key at a coarser unit: date:date@month puts every order of a month in one group. The column is checked as a date (a cell like 2026-02-30 is refused, with its line), not trusted as text.

a real run
$ table --where 'status = paid' --group date:date@month --agg 'count,sum:price:dec(2)' \
    --sort date --format csv orders.csv
date,count,sum:price
2026-01-01,31,691.37
2026-02-01,28,738.90
2026-03-01,43,1196.80
2026-04-01,33,774.77
2026-05-01,31,661.19
2026-06-01,39,858.18
Reading it. 2026-03 was the strongest month, with 1196.80 euros from 43 paid orders. The six counts add up to the 205 paid orders of the file, which is checked when this page is generated.

6 · Two files

a join--join--on

“The orders know the customer by a number. The country is in another file. Which country buys the most?”

One hash join: the --join file is read whole into a bounded table, the orders stream past it. The output row is the order’s cells followed by the customer’s; a column name in both files is refused, never silently renamed. The same plan then groups by a column that came from the other file.

a real run
$ table --join customers.csv --on customer_id --where 'status = paid' --group country \
    --agg 'count,sum:price:dec(2)' --sort -sum:price --format csv orders.csv
country,count,sum:price
FR,94,2329.47
ES,74,1780.70
PT,28,575.76
IT,9,235.28
Reading it. FR leads with 2329.47 euros, then ES. The totals are those of a recount of the two files in Python by customer country, checked when the page is generated. --join-type left, semi and anti answer “who never ordered” in the same way.

7 · The same bytes on any number of cores

determinism--threads

“It is fast enough on four cores. But will the totals be the same as on one?”

The shop has grown. A file of 120,000 rows (2.0 MB; it is generated by this page’s script, seed 5) is grouped into 100 groups with an exact sum and an exact mean, once on one thread, once on two, once on four. SHA-256 of everything the tool printed:

Reading it. The three digests are identical. A group sum is exact, so the order in which threads add rows cannot change a digit; a refusal names the same row, line and column whatever the thread count. The project’s CI compares such digests across Linux x86-64, Linux arm64 and macOS arm64.

Part II · In the lab and in the field

The same tool on four small datasets from the sciences: a growth plate, a titration, a temperature logger, a survey. The data are invented; the runs are real.

8 · A growth plate

biology: groups of replicates--group A,Bmean:COL:dec(3)@3

“Three compounds, eight doses, four wells each, a blank row. Which compound stops the bacteria at the lowest dose?” — a PhD student

The plate reader’s export has one row per well. Group by compound and by concentration, average the optical density of the four replicates exactly (the mean of exact decimals is rounded once, half to even, to the scale you ask for: @3), and leave the blank wells out.

a real run
$ table --where 'compound != blank' --group 'compound,conc_uM:dec(2)' --agg \
    'count,mean:od600:dec(3)@3' --sort compound --format csv plate.csv
compound,conc_uM,count,mean:od600
A,0.01,4,1.062
A,0.03,4,1.053
A,0.10,4,1.013
A,0.30,4,0.867
A,1.00,4,0.530
A,3.00,4,0.265
A,10.00,4,0.162
A,30.00,4,0.136
...
Reading it. Compound A has collapsed the culture by the 3 µM wells (mean 0.265); B needs about three times more (0.332 at 10 µM); C is still at 0.798 at 30 µM. Every mean is the exact mean of four decimals rounded once; the blank wells (8 of them, mean 0.0410) are what to subtract if the lab does so. The figure is drawn from the 24 group means; the first rows of the CSV are shown above.

9 · Burette readings

chemistry: a declared precisionmean:COL:dec(2)@3value.decimal-scale

“Three analysts, eight titrations each. Does anyone read the burette differently? And one of them wrote a third decimal.”

A burette is read to a hundredth of a millilitre, so the column is declared :dec(2): the mean of the readings is exact and is printed to three digits (@3). A reading with a third digit would have been rounded by almost any tool; here it is refused, with the line and the value.

a real run
$ table --group analyst --agg \
    'count,mean:volume_ml:dec(2)@3,min:volume_ml:dec(2),max:volume_ml:dec(2)' --sort \
    analyst --format csv titration.csv
analyst,count,mean:volume_ml,min:volume_ml,max:volume_ml
Ines,8,24.338,24.25,24.42
Marc,8,24.462,24.36,24.56
Sara,8,24.294,24.21,24.41

10 · Two days of a temperature logger

physics: a stream of readings--input-format jsonl--group ts:timestamp@hour

“The logger writes one JSON line every five minutes. What did the hut do over two days?”

The logger’s file is JSON lines, not CSV. --input-format jsonl --fields ts,temp_c reads two keys of each line; ts:timestamp@hour groups the readings by hour. The minimum, maximum and mean are floats here (a temperature is a measurement, not an amount): the tool says so with :float.

a real run
$ table --input-format jsonl --fields ts,temp_c --group ts:timestamp@hour --agg \
    count,min:temp_c:float,max:temp_c:float,mean:temp_c:float --format csv \
    sensor.jsonl
ts,count,min:temp_c,max:temp_c,mean:temp_c

Reading it. 48 hours of 12 readings each (576 lines). The warmest hour is 2026-03-05T11:00:00Z, with a maximum of 21.89 °C; the coldest is 2026-03-06T23:00:00Z, with a minimum of 8.16 °C. The days repeat, and the hourly mean follows the day while the band shows the spread inside the hour.

11 · Who answered, and how many times?

social science: counts and duplicates--group A,Bdistinct:COL

“Four hundred answers about the new tram line. How do the districts split, among adults? And are there people who answered twice?”

Two group keys make a crosstab; count counts rows and distinct:respondent counts people. Before any percentage, ask whether rows are people:

a real run

  "truncated": false,
  "next": null,
  "group_count": 1
}
a real run
$ table --where 'age:int >= 18' --group district,answer --agg \
    count,distinct:respondent --sort district --format csv survey.csv
district,answer,count,distinct:respondent

Centro,unsure,28,27

Reading it. The file has 400 rows but only 380 respondents: 20 people answered more than once, and a percentage of rows would count them twice. Among adults, Sur has the largest share of yes and Norte the largest of no (the bars). The next step, a test of whether the districts differ, is a job for cancho-stats, which reads the same CSV.

12 · What did each channel cost, and earn?

marketing: two files, exact money--groupsum:COL:dec(2)

“Finance wants spend and revenue by channel, to the cent, and wants it to add up.” — a marketing analyst, on the first of the month

Two exports: the ad platforms’ weekly spend (spend.csv) and the orders the shop credits to a channel by last click (sales.csv). Money is the case :dec(2) exists for: each sum is the exact sum of the cents, and a cell with a third decimal would be refused, never rounded.

a real run
$ table --group channel --agg 'sum:spend:dec(2)' --sort channel --format csv spend.csv
channel,sum:spend
display,9209.87
email,1163.69
search,7275.22
social,11105.22
a real run
$ table --group channel --agg 'count,sum:revenue:dec(2)' --sort channel --format csv \
    sales.csv
channel,count,sum:revenue
display,71,2783.84
email,101,6365.93
search,325,16775.71
social,143,6828.12
Reading it. Dividing the second table by the first (the page does that arithmetic, on the printed numbers) gives the revenue credited per euro of spend: 5.47 euros for email, 2.31 for search, 0.30 for display. Both files were recounted in Python’s decimal when this page was generated. One warning belongs next to the table: credited is not caused. Last click credits whoever the customer touched last, and a search ad is often the last thing touched by someone who had already decided; whether an ad earns money that would not have come anyway is the question of stories 12 to 14 of cancho-stats.

13 · From the raw tables to the holdout analysis

marketing: join, window, per-arm totals--join--where date:datedistinct:COL

“The experiment tool gave me who was shown the ad and who was held out. The shop gave me purchases. I need, per arm: users, buyers, revenue.”

Two tables, and the counting rules matter more than the tool: purchases made before the campaign started do not belong to it, and a user who bought twice is one buyer. First the denominators, then one join of the purchases to the arm of each user, restricted to the campaign window, counting purchases, distinct buyers and the exact revenue:

a real run
$ table --group arm --agg count --sort arm --format csv campaign_users.csv
arm,count
ads,4000
holdout,4000
a real run
$ table --join campaign_users.csv --on user_id --where 'date:date >= 2026-09-01' \
    --group arm --agg 'count,distinct:user_id,sum:amount:dec(2)' --sort arm --format \
    csv campaign_purchases.csv
arm,count,distinct:user_id,sum:amount
ads,285,250,13812.61
holdout,228,196,11682.33
Reading it. 250 buyers among 4000 users shown the ad, 196 among 4000 held out; revenue 13812.61 and 11682.33 euros. 229 purchases in the file were made in August, before the start, and the --where left them out; counting them would have made both arms look better and the campaign look no different. These four numbers per arm are what the significance question needs: stats ci prop on the buyer counts, and stats ci diff or resample perm on the per-user revenue (see cancho-stats, story 12, for exactly this analysis). Producing a per-user file for it is one more --group user_id.
