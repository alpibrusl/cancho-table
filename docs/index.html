Exact answers from CSV and JSON lines, or a refusal that tells you how to fix the question.

table is a command line for people and AI agents. Numbers you declare are exact, every limit is a rule, the same bytes come back on any number of cores, and a refusal carries the repair as a command to run.

Trust the answer, not the chat

Most data tools optimise for flexibility. table optimises for predictability.

Exact numbers

Write :int, :dec(S) or :float and the column is read as that number. A cell with more digits than the scale is refused, never rounded; a float sum is rounded once. :date, :timestamp and :datetime read days and times the same way: a real calendar, no zone guessed.

Bounded by rules

Rows, line and record size, groups, distinct values and group state each have a limit with its own rule, listed by table introspect. Measured memory is in the results.

Same bytes on any number of cores

--threads N gives the one-core answer, a refusal included. Asking for more cores changes the time, not the output.

Refusals that carry a repair

A refusal is one JSON line with a rule, a hint in a sentence (on every rule but three operating-system errors) and a repair: a command to run, a choice of commands, or the reason there is none.

How it works

Filter on decimals

price:dec(2) reads the column as exact decimals with two fractional digits: 12.5 and 12.50 are one value, and the literal is read at the same scale. A cell with more digits than the scale is refused, never rounded, and the repair is the command with the scale the column needs. This example uses a small prices.csv.

$ table --where "price:dec(2) >= 12.50" --format csv prices.csv
item,category,price
book,office,12.50
lamp,home,12.5

Filter and find the extremes of floats

temp:float reads the column as the nearest double (ties to even), and compares doubles, not text: 21.5, 21.50 and 2.15e1 are one value. min and max print as the shortest decimal that reads back to the same double; rows are copied as they are. NaN, inf, an out-of-range number and a cell that is not a number are refused, never skipped, with the row, line and column; for NaN the hint is the idiom that keeps those rows out (temp != 'NaN' and temp:float >= 21.5), and there is no repair, because what the cell was meant to be is not known. min, max, distinct, count, sum and mean work on floats. A column really named x:float is written x\:float.

$ table --where "temp != 'NaN' and temp:float >= 21.5" --format csv readings.csv
sensor,temp
a,21.5
c,21.50
d,2.15e1
$ table --where "temp != 'NaN'" --agg "min:temp:float,max:temp:float,distinct:temp:float" --format csv readings.csv

-3.4,21.5,3

Sum and average floats, exactly

sum:x:float and mean:x:float are exact: every cell is added without rounding and the total is rounded once to the nearest double (ties to even), so the answer does not depend on the order of the rows or on the number of cores. Adding the same numbers left to right in double precision gives 0.0 for group a and 0.9999999999999999 for group h. A mean takes no @N (it is a double; mean:x:float@2 is refused). A sum beyond the largest double, about 1.8e308, is agg.float-overflow, which names the group; the mean of that group still exists. On a file of 2,000,000 doubles (the committed runs of scripts/threads_vs_duckdb.py) DuckDB’s DOUBLE sum printed a different value for different thread counts and, for different runs of the same command (on the Mac at 2 and 4 threads; on Linux at 2, 4, 8 and 16 threads); it equalled the exact sum in 1 of 15 runs on the Mac and 0 of 15 runs on Linux. Its kahan_sum and a DECIMAL sum are in the side by side too. An earlier measurement, on a million rows, gave a different answer at 1, 4 and 16 threads, none equal to the exact one (see the benchmarks). (benchmarks)

$ table --group g --agg "sum:x:float,mean:x:float" --format csv drift.csv

h,1.0,0.1

Sum and average decimals

sum:price:dec(2) is exact and printed at the column's scale. mean:price:dec(2)@3 is the exact quotient rounded half to even at three digits (@N is required for a whole-number column), the same on any number of cores. distinct counts by value, so 12.5 and 12.50 are one. Sums are exact at any width. A column whose name really ends in :int, :dec(2) or @2 is written with a backslash: sum:x\:dec(2).

$ table --group category --agg "sum:price:dec(2),mean:price:dec(2)@3" --format csv prices.csv
category,sum:price,mean:price
home,15.70,7.850
office,14.00,7.000
$ table --agg "min:price:dec(2),max:price:dec(2),distinct:price:dec(2)" --format csv prices.csv

Group and sort by numbers

--group and --order-by take the same suffixes as --where: :int, :dec(S), :float and, for days and times, :date, :timestamp and :datetime (the key of an instant is written in UTC, 2026-01-01T23:00:00Z, whichever offset the first cell had). The key is the value of the cell, not its text. Here 1.5, 1.50, 01.5 and +1.5 are one group at :dec(2), written back at the column's scale, where grouping by text gives four groups for them. Groups come out in numeric order, and --order-by -price:dec(2) puts 12.50 before 3.2, where a text sort puts 3.2 first; rows that tie keep their order in the file. On a million rows with a number written in two spellings (20,001 values), csvtk and Miller grouped by text and reported 22,002 groups: see the benchmarks.

Check what is in a column

--report types reads the file once and prints, for each column, how many cells are empty, whole numbers, decimals, floats or something else, the widest decimal scale, the first row and line that each declaration would refuse, and a suggested declaration: :int, :dec(S), :float, or none when a cell is not a number. It prefers the exact reading: a column of 0.1-shaped cells is :dec(1), not :float. It never changes anything; no other flag reads a column as a type unless you write the suffix, and the report is the same on any number of cores. Here price has an n/a in its last row (suggestion none, first offender row 4, line 5), bytes has a 1e3 (:float, not :int) and cents has an empty cell (still :int; the empty cell is counted apart and refused by any numeric reading). On a million rows with three late wrong cells, DuckDB's type sniffing, which looks at a sample of 20,480 rows, still said DOUBLE and BIGINT, and its SUMMARIZE failed at line 900,001; Miller's summary showed the mixtures without counts or rows (benchmarks). --report dates does the same for days and times: for each column it counts the cells that are a :date, a :timestamp, a :datetime or something else, and suggests the declaration when every non-empty cell is of one of them.

Sort rows

--order-by takes keys: - before a name is descending, :int compares whole numbers, and rows that tie keep their order in the file. With --limit or --top it keeps only the best rows, so memory stays flat. A full sort holds every row, up to --max-sort-rows (1,000,000 by default); past that it refuses and suggests --top, a smaller --limit or a --where. There is no sort that spills to disk.

$ table --where "bytes != ''" --order-by -bytes:int,status --limit 3 --select id,customer,bytes --format csv orders.csv
id,customer,bytes
3,"Doe, Jane",2048
1,"Doe, Jane",512
4,Acme,128

Rename columns

--rename TARGET=NEW,... gives the columns of rows or groups the labels the next step expects, without a second tool in the middle: TARGET is a label as the answer prints it (customer, count, sum:bytes) or #N, its place (the way to name a label two columns have), and NEW is at least one byte. It changes the csv header, the JSON columns and the keys of JSON lines, and nothing else: --where, --group, --agg and --order-by keep naming the columns of the file, and --sort names the label after the rename (--rename sum:bytes=total --sort -total). In a query it is select customer as name: as is required, an alias wins over a file's column in order by, and where and group by do not see it. A target that is not a column of the answer is rename.unknown-target and lists the labels it could have been, a label two columns have is rename.ambiguous-target, and one column renamed twice is rename.repeated-target.

$ table --where "bytes != ''" --group customer --agg count,sum:bytes --rename customer=name,sum:bytes=total --sort -total --format csv orders.csv
name,count,total
"Doe, Jane",2,2560
Acme,1,128
Zed,1,64
$ table --query "select customer as name, sum(bytes) as total from 'orders.csv' where bytes != '' group by customer order by total desc" --format csv
name,total
"Doe, Jane",2560
Acme,128
Zed,64

Join two files

--join FILE --on PROBE=BUILD joins the file you name (or standard input) with a second one. The operand is the probe side and is streamed; the --join file is the build side and is held in memory, only the columns the plan names, counted in --max-state-bytes. --join-type is inner (the default: each probe row, in the probe's order, once for every build row with its key, in the build's order, followed by that row's cells), left (the same, and a probe row with no match once, with every cell of the build row empty: there is no null), semi (each probe row that has a match, once, with its own cells) or anti (each probe row that has none, once). A key is compared as text, byte for byte (007 is not 7, and an empty cell matches an empty cell: there is no null), or as a number when the pair ends in a type, --on id=user:int (also :dec(S) and :float, and :date, :timestamp and :datetime, where two spellings of one instant are one key): then 007 is 7, -0 is 0, 1.5 is 1.50, and a cell that is not of the type, an empty one included, is refused. --on a=x,b=y is a key of two pairs (up to eight); --on id names a column both files have, and the answer shows it once. Two files that share a column name are refused as join.column-collision, and the refusal offers the invocation with a --join-prefix. A number read from a padded cell of a left join (--where "tier:int > 1") is refused as any empty cell is, and the refusal says padded. --group, --agg, --sort, --order-by, --top, --limit, --from and --rename take the joined row as they take a file's, and the groups or the sorted rows share --max-state-bytes with the --join file, which is held first (a group that does not fit in what the build leaves is limit.state-too-large with detail.holder groups and detail.build_bytes). --join-where EXPR is a --where over the --join file's own columns, applied to its rows before they are held: the ON of a SQL join, so that a left join keeps its probe row, padded, where the same condition in --where drops it. And the leading run of text conditions in --where (no type, none after the first typed one) is applied before the join, to the probe row before its key is read, and for an inner join to the build row before it is held, so --where "bytes != '' and bytes:int > 100" guards a typed key as it guards a typed column; --explain says which conditions went where (docs/joins.md, sections 16 to 18). A --join file that does not fit is limit.state-too-large, and when the call can be run with the two files exchanged and give the same rows (an inner join, a probe file that is smaller on disk and fits as the build side, no --join-prefix, --join-where or column named by position, and an answer that is not a page of rows) the refusal's repair is that call: the rows come in the other file's order and the columns as they were, and --explain says in join.build_state.swap whether it would be offered (section 22). A --join file too large to hold whose key is in order, like the operand's, is joined with --join-sorted: a merge that reads each file once and holds the rows of one key of the --join file at a time, in the same bytes, and refuses the first row of either file out of order as join.not-sorted (section 23).

Ask in a small SQL

--query takes one statement of a small subset of SQL (select, from, where with and, group by, order by, limit and offset) and means exactly the flags it is translated to: there is one plan, and the same question asked in flags gives the same bytes. select a as b gives a column of the answer another label (it is --rename '#1=b'). A join is written from 'orders.csv' as o [inner|left|semi|anti] join 'tiers.csv' as t on o.customer = t.customer [and t.tier != 'bronze']: as names both tables, every column is written alias.column (the only bare name is the as name of a select item, in order by), the on is key equalities (one column of each table, up to eight) and then conditions on the second table alone, which are the ON of the join (--join-where), and the second table's columns are named t.tier in the answer: it is exactly the flags of the join above. What the subset leaves out (expressions, like, null, a right, full or cross join, a second join, subqueries) is refused with the feature named and what to write instead, and a mistake is refused at the byte where it is, with a corrected command when the correction is certain. docs/query.md has the grammar.

See the plan before it runs

--explain takes the flags (or the --query) of a call and prints, as one JSON line, what the call would do, without doing it: each column the plan names and where the header puts it, every condition, group, aggregate and order with the type it is read as, the page, the kind of work it is and the limits in force, how many threads it would use and why not more, the rules the data could still refuse it with, and notes. It opens the file and reads its first 64 KiB for the header, and nothing after the header: no row is framed, counted or judged, so what it costs does not grow with the file (docs/query.md section 15 has the measured time). It does not read standard input at all, so the columns of a plan on a pipe are not known, and the notes say so. A plan the run would refuse before it read a row (a bad flag or query, a name the header lacks, a missing file, a header past --max-line-bytes) is refused with the run's own error and exit status.

What it cannot do yet

Status: early. What is listed on this page works and is tested; what is missing is listed here. The program is built with one pinned compiler version, and that compiler is still changing.

  • Dates and timestamps are built as far as the four slices of docs/datetime.md (T0 to T3): :date, :timestamp and :datetime work in --where, --group, --agg (min, max, distinct and count) and --order-by, equal instants are equal whatever their offsets, and a cell that is not a real date, has 24:00, a leap second, seven fractional digits, a zone name, -00:00 or no offset where one is needed is refused with its own rule and, when it can be written, the repair. A group key may be a period (--group ts:timestamp@day, d:date@month, w:datetime@hour; the units are hour, day, month and year, slice T2): the key is the first value of the period, a value of the same type, and the day of a :timestamp is the UTC day of its instant. --query reads them (ts::timestamp, cast(d as date)), a join takes them as a key (--on seen=at:timestamp: instants in two offsets match) and --report dates counts them and suggests the declaration (slice T3). Not yet: @week, a period in --query or in a join key, epoch integers, zone names, arithmetic; and never a sum or a mean of dates.
  • Numbers are mostly built. :int, :dec(S) and :float work in --where, --agg, --group and --order-by. Columns of 15- to 17-digit numbers are read by an exact reader that allocates nothing on the paths a real column takes (Clinger, then Eisel-Lemire, then an exact fallback); it matched Python's float() on every cell of each differential run, the largest of 100,367,328 cells (the final code), and costs 29.6 ns a cell against 1,151 ns before (one Mac core, load average 6.7 to 13.5; conditions).
  • A sort uses more cores only for a whole sort written as CSV. With --order-by, --format csv and no --top, --limit or --from, --threads above 1 sorts in parallel and gives the same bytes; pages, --top and JSON output run on one core. A threaded sort peaks at 11.8 to 14.8 times the size of a 39.55 MB file at 16 threads on the Mac, against 4.4 to 6.2 times for the sequential sort (conditions). There is no sort that spills to disk.
  • One join, in seven slices of it** (J1 to J3, J3b, J5, J7 and J9 of docs/joins.md): --join FILE --on KEYS joins the operand (or standard input) with a second file, as an inner, left, semi or anti join, on up to eight pairs of columns, each compared as text or, with a type (:int, :dec(S), :float, :date, :timestamp, :datetime), as a number or an instant, giving rows, sorted rows or groups (--select, --where, --join-where, --group, --agg, --sort, --order-by, --top, --limit, --from, --rename, --format). No right or full join, no --report over a join (write the join as csv and pipe it into a second call). Either file may be JSON lines (--input-format jsonl --fields ... for the operand or standard input, --join-input-format jsonl --join-fields ... for the --join file, each defaulting to the operand's) and a csv --join file may have a delimiter of its own (--join-delimiter); a JSON-lines row is held as the csv record of its cells, so it counts in --max-state-bytes as the csv row with the same cells would. A --query says the same join (from 'a.csv' as a join 'b.csv' as b on a.k = b.k, every column written alias.column), as one statement; the MCP server has the flags as properties (join, on, ...) and no query with a join, since a query that names its source has no file or stdin to go with it. The --join file is held in memory, only the columns the plan names, counted in --max-state-bytes together with the groups or the sorted rows (resident memory can be up to about three times that while it grows), and nothing spills to disk; past the bound the refusal offers the call with the two files exchanged when that gives the same rows and the other file fits. With --join-sorted, which says that both files are in ascending order of the key (bytewise for text, by value for a typed key), the join is a merge of the two instead: each file is read once, in step, only the rows of one key of the --join file are held at a time (so a --join file much larger than --max-state-bytes runs when no key it shares with the operand repeats enough rows to pass it), the answer is the answer of the same call without the flag, and the first row of either file whose key is below the one before it is join.not-sorted; it takes no --query. A join is read on one core whatever --threads says.
  • One input at a time otherwise: a file named on the command line, or standard input (-, or no file), read in one pass on one core, in blocks, at about the speed of a named file on one core. A producer that writes slowly is waited for until the first 512 bytes arrive; a closed descriptor 0 reads as empty; a descriptor that fails is refused with an io.* rule (docs/readers.md 11.1, 11.7). (docs/readers.md, section "R1 as built").
  • JSON lines are read, nothing else is. --input-format jsonl (or ndjson) reads one JSON object per line, from a file or from standard input, with the columns declared by --fields (paths such as user.name or items.0.sku; --discover reports what the first lines hold). A number is the cell its exact text is, never through a double. A line that is not strict JSON, not an object, a declared path with no value, an object or an array in a cell, and a key twice are tagged refusals (docs/readers.md section 12). --format jsonl writes the answer back as JSON lines (one object per row, keys the output columns, every value a string but the aggregates and the group keys that have a type (--group NAME:int, NAME:dec(S), NAME:float), which are numbers; docs/readers.md section 13). No Parquet, no JSON array or pretty-printed document (use jq -c '.[]'). CSV and TSV (comma, tab or semicolon) as before.
  • --query is a small subset of SQL, not SQL: or, not and parentheses are there (a level is all and or all or: a = 1 or b = 2 and c = 3 is refused as query.mixed-and-or, with both readings as the repair; not a = 1, not (...), a not in (1, 2), a not contains 'x'), and as names a column of the answer, but no expressions or functions, no like, no null, no subqueries, one join and no more (inner, left, semi or anti, every column written alias.column), and a grouping sorts by one column. Each is refused as query.unsupported, with the feature named (docs/query.md).
  • No guessing. Every column is text unless you declare :int, :dec(S), :float, :date, :timestamp or :datetime; --report types suggests a declaration and applies none. No computed column (a renamed one is --rename customer=name, a label and nothing else: the filter, the grouping and the sort by header still name the header's columns); or, not and parentheses are there in a filter (a mix of and and or at one level is refused with both readings, never guessed; a typed cell is read only when its condition is reached, so c = '' or c:int > 5 keeps the empty cells and c:int > 5 or c = '' refuses the first one).

The rest of joins is on the backlog, in rough order. Nothing there is promised.
