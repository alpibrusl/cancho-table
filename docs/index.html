A deterministic data primitive for AI agents.

Query CSV and TSV data with explicit semantics, bounded resources, structured refusals, and machine-verifiable capabilities.

Ask a CSV a question, get an exact answer: with a command line and flags, not a chat box. The same tool for a person and for an agent.

One complete flow

Ask, get refused with a repair, run the repair. The repair is the corrected command, and every line below is what the built program prints, on the five-line file shown under “What you can do now”.

# Ask: the customer and bytes of the orders with status 200
$ table --where "status = 200" --select Customer,bytes orders.csv
{"rule": "select.unknown-column", "hint": "pick from detail.available", "repair": {"kind": "choose", "options": [{"argv": ["table", "--where", "status = 200", "--select", "customer,bytes", "orders.csv"]}]}}
# exit status 3; the rule, hint, repair of the JSON line it prints
# The tool offered the corrected command. Run it:
$ table --where 'status = 200' --select customer,bytes orders.csv
{"ok":true,"command":"table","schema":"table.v2","data":{"columns":["customer","bytes"],"rows":[["Doe, Jane","512"],["Doe, Jane","2048"],["Zed","64"]],"row_count":3,"truncated":false,"next":null},"meta":{"version":"0.3.0"}}

Why table?

Most data tools optimise for flexibility. table optimises for predictability.

  • Explicit typesA column is text unless you write :int (an exact 64-bit integer), :dec(S) (an exact decimal with S fractional digits) or :float (the nearest double, in --where and for min, max, distinct, count); a cell that is not one is refused. docs/filter.md
  • Explicit operationsOne plan from flags, resolved against the header before any row is read. No expressions, no functions. docs/filter.md
  • Bounded resource useRows, line and record size, groups, distinct values and group state each have a limit with its own rule (the limits). Peak memory was about 2 MB on a 31.7 MB file (Linux) and 1.6 to 1.8 MB on a 1 GB file (Mac, one core). Benchmarks
  • No implicit network accessThe authority row below lists what the program can reach: no net_out, net_in, ffi or clock, and nothing written to disk. cancho authority derives it, and CI fails if the binary differs from the committed manifest. docs/architecture.md
  • Machine-readable errorsOne JSON line against a schema (table.v2). A refusal is {code, rule, message, hint, repair, detail}. docs/refusals.md
  • Repair hintsA refusal says how to fix the request: a command to run, a choice of commands, or why there is none. docs/refusals.md
  • Capability introspectiontable introspect prints the flags, limits, rules and authority; table skill prints a guide for an agent. Excerpts below
  • The same bytes on any number of cores--threads N gives the one-core answer, the same refusal included. docs/parallel.md

What you can do now

Every example runs on this five-line file, and the output is what the program prints.

id,customer,status,bytes
1,"Doe, Jane",200,512
2,Acme,404,
3,"Doe, Jane",200,2048
4,Acme,500,128
5,Zed,200,64

Pick some columns

Name them; they come out in the order you give. A comma inside a quoted field stays inside it, and the output is quoted again.

$ table --select customer,bytes --format csv orders.csv
customer,bytes
"Doe, Jane",512
Acme,
"Doe, Jane",2048
Acme,128
Zed,64

Keep the rows that match

Text compares byte by byte; :int compares whole numbers exactly. Conditions run left to right and stop at the first false one, so the first one here keeps the empty cell away from the number test.

$ table --where "bytes != '' and bytes:int > 100" --select id,customer --format csv orders.csv
id,customer
1,"Doe, Jane"
3,"Doe, Jane"
4,Acme

Filter on decimals

price:dec(2) reads the column as exact decimals with two fractional digits: 12.5 and 12.50 are one value, and the literal is read at the same scale. A cell with more digits than the scale is refused, never rounded, and the repair is the command with the scale the column needs. This example uses a small prices.csv.

$ table --where "price:dec(2) >= 12.50" --format csv prices.csv
item,category,price
book,office,12.50
lamp,home,12.5
$ table --where "price:dec(1) >= 12.5" prices.csv
{"rule": "value.decimal-scale", "hint": "declare a larger scale, :dec(N) with N the most fractional digits the column holds", "repair": {"kind": "choose", "options": [{"argv": ["table", "--where", "price:dec(2) >= 12.5", "prices.csv"]}]}}
# exit status 8; the rule, hint, repair of the JSON line it prints

Filter and find the extremes of floats

temp:float reads the column as the nearest double (ties to even), and compares doubles, not text: 21.5, 21.50 and 2.15e1 are one value. min and max print as the shortest decimal that reads back to the same double; rows are copied as they are. NaN, inf, an out-of-range number and a cell that is not a number are refused, never skipped, with the row, line and column; for NaN the hint is the idiom that keeps those rows out (temp != 'NaN' and temp:float >= 21.5), and there is no repair, because what the cell was meant to be is not known. min, max, distinct and count work on floats; sum and mean do not yet. A column really named x:float is written x\:float.

$ table --where "temp != 'NaN' and temp:float >= 21.5" --format csv readings.csv
sensor,temp
a,21.5
c,21.50
d,2.15e1
$ table --where "temp != 'NaN'" --agg "min:temp:float,max:temp:float,distinct:temp:float" --format csv readings.csv
min:temp,max:temp,distinct:temp
-3.4,21.5,3
$ table --where "temp:float >= 21.5" readings.csv
{"rule": "value.not-finite", "hint": "keep them out with --where first: x != 'NaN' and x:float > 5 never reads the NaN cell as a number", "repair": {"kind": "none", "reason": "what the cell was meant to be is not known"}, "detail": {"path": "readings.csv", "context": "where", "column": "temp", "row": 6, "line": 7, "value": "NaN", "value_truncated": false}}

Sum and average decimals

sum:price:dec(2) is exact and printed at the column's scale. mean:price:dec(2)@3 is the exact quotient rounded half to even at three digits (@N is required for a whole-number column), the same on any number of cores. distinct counts by value, so 12.5 and 12.50 are one. Sums are exact at any width. A column whose name really ends in :int, :dec(2) or @2 is written with a backslash: sum:x\:dec(2).

$ table --group category --agg "sum:price:dec(2),mean:price:dec(2)@3" --format csv prices.csv
category,sum:price,mean:price
home,15.70,7.850
office,14.00,7.000
$ table --agg "min:price:dec(2),max:price:dec(2),distinct:price:dec(2)" --format csv prices.csv
min:price,max:price,distinct:price
1.50,12.50,3

Sort rows

--order-by takes keys: - before a name is descending, :int compares whole numbers, and rows that tie keep their order in the file. With --limit or --top it keeps only the best rows, so memory stays flat. A full sort holds every row, up to --max-sort-rows (1,000,000 by default); past that it refuses and suggests --top, a smaller --limit or a --where. There is no sort that spills to disk.

$ table --where "bytes != ''" --order-by -bytes:int,status --limit 3 --select id,customer,bytes --format csv orders.csv
id,customer,bytes
3,"Doe, Jane",2048
1,"Doe, Jane",512
4,Acme,128

Count and sum by a key

count, sum, min, max, mean and distinct, of whole numbers and of :dec(S) columns, sorted by what you ask for. Sums are exact at any width: a sum past 64 bits is printed in full (up to 28 digits), and it is the same on any number of cores.

$ table --where "bytes != ''" --group customer --agg count,sum:bytes --sort -sum:bytes --format csv orders.csv
customer,count,sum:bytes
"Doe, Jane",2,2560
Acme,1,128
Zed,1,64

Page through the results

JSON answers come in pages. next tells you where the next one starts. Resuming re-reads the file from the start, so paging deep into a huge file gets slow.

$ table --select id,customer --limit 2 orders.csv
{"ok":true,"command":"table","schema":"table.v2","data":{"columns":["id","customer"],"rows":[["1","Doe, Jane"],["2","Acme"]],"row_count":2,"truncated":true,"next":{"from":2}},"meta":{"version":"0.3.0"}}
$ table --select id,customer --limit 2 --from 2 orders.csv
{"ok":true,"command":"table","schema":"table.v2","data":{"columns":["id","customer"],"rows":[["3","Doe, Jane"],["4","Acme"]],"row_count":2,"truncated":true,"next":{"from":4}},"meta":{"version":"0.3.0"}}

Get CSV back

--format csv writes the rows as CSV as they are read, whatever the file size. Every column when you do not pick any. A non-zero exit means the output is only the start of the answer.

$ table --where "status = 200" --format csv orders.csv
id,customer,status,bytes
1,"Doe, Jane",200,512
3,"Doe, Jane",200,2048
5,Zed,200,64

Use several cores

--threads N reads the file with N cores (1 to 64). The answer is the same bytes as with one core, refusals included. Files under 1 MiB are read on one core whatever you ask, so this tiny example only shows the same answer.

$ table --threads 4 --group status --agg count --format csv orders.csv
status,count
200,3
404,1
500,1

See what a bad request looks like

A refusal has a fixed rule name, an exit status and, where one exists, a repair. A cell that is not a whole number, an empty one too, is refused with its row, line and column; there is no repair here, because what the cell was meant to be is not known.

What it cannot do yet

  • Floats are partly built. :float works in --where and for min, max, distinct and count. Not yet: sum and mean of a float (coming next: exact, and the same on any number of cores), grouping by a float column by value, and --order-by on a float.
  • Decimals are mostly built. :dec(S) filters and aggregates (sum, min, max, mean, distinct, count). Not yet: grouping by a decimal column by value and --order-by price:dec(2) (docs/numbers.md).
  • One core for a sort. --threads is accepted with --order-by and gives the same bytes, but the sort runs on one core. There is no sort that spills to disk.
  • No joins, and one input file at a time, named on the command line (no standard input).
  • No JSON lines, no Parquet. Only CSV and TSV (comma, tab or semicolon).
  • No guessing. Every column is text unless you say :int. There is no mean, no computed or renamed column, no or in a filter.

JSON lines, joins, mean, decimals and standard input are on the backlog, in rough order. Nothing there is promised.

Quick start

You need Rust, git, clang and Python 3. On a 16-core Mac with Rust installed and its dependencies already downloaded, the compiler built in 19 seconds and table in 3. The clones and a first-time dependency download are extra: allow a few minutes the first time.

git clone https://github.com/alpibrusl/cancho
git clone https://github.com/alpibrusl/cancho-table && cd cancho-table
REV=$(sed -n 's/^cancho *= *"\([0-9a-f]*\)".*/\1/p' cancho.toml)
(cd ../cancho && git fetch -q origin && git checkout "$REV" && cargo build --release -p cancho)
export PATH=$PWD/../cancho/target/release:$PWD/build:$PATH
cancho build                       # builds build/table

Built in cancho, with an authority the compiler wrote

cancho is a language whose compiler writes down what a program may do (cancho authority). For table that is the line below: it can read its arguments and the file, allocate memory, start threads and write to the terminal. It cannot use the network, call foreign code, read the clock or write a file. CI fails if the binary says otherwise. Why each label is there, and what a row cannot say: docs/architecture.md.

# manifests/table.authority.json
table    args, conc, dir_read, err_write, file_read, fs_read(""), heap, io_write
# bounded: true; foreign symbols: none; net_out, net_in, ffi, clock: absent

How fast

Supporting evidence, not the point: predictability costs little speed. A core is one of the independent workers inside a processor; table uses one by default and --threads 16 uses sixteen. DuckDB is a full database engine and a popular, fast way to query a CSV, so it is a fair yardstick. On these four questions one core of table is about as fast as, or faster than, DuckDB on all sixteen; with many distinct keys in a group-by, DuckDB on all cores wins.

Best of five runs, output thrown away, each tool’s answer checked against a Python answer first. csvtk 0.38.0 on one core (its filter is filter piped to grep); DuckDB 1.5.6. DuckDB’s 16-core times for filter and pick-2-columns are from an earlier run on the same machine. Miller is not installed on the Mac: on a different machine (Linux, 6 shared cores) Miller took 0.300 s to filter, 0.438 s to count and 0.649 s to sum, against table’s 0.074, 0.128 and 0.140 s there. All the tables, and how to rerun them.

Filtering on a decimal column (price:dec(2) >= 500.00) costs up to about 10 percent more than on a whole-number column: 0.070 s on one Mac core for 1,000,000 rows, against 0.186 s for DuckDB on one core. Summing and averaging a decimal column by a key takes 0.085 s on one Mac core, 2.5 times faster than DuckDB; DuckDB’s floating-point sum gave different, slightly wrong answers at one and at sixteen threads, while table’s exact sum did not change. Filtering a float column with two decimals is 2.9 times faster than DuckDB’s DOUBLE on one Mac core; a column of 17-digit numbers is the exception, where min and max take 1.09 s against DuckDB’s 0.208 s. The numbers.

Where it is slower

  • A group-by with a million distinct keys: 3.4 times slower than DuckDB on one core, and 9.4 times slower than DuckDB on all 16 (Mac). More cores do not help it.
  • Sorting rows: 1,000,000 rows by a number take 0.41 s on one core, level with DuckDB on one core (0.43 s) but 3.4 times slower than DuckDB on all 16 (0.12 s), because the sort runs on one core (Mac). On Linux a sort with many ties is 1.45 times slower than sort -s -n.
  • distinct over a column of unique values: 1.4 times slower than DuckDB on one core.

Status: early

  • What is listed above works and is tested. The list of what is missing is above too.
  • The speed numbers are for one file shape on two machines, plus a set of harder cases on the benchmarks page, where it loses some.
  • The program is built with one pinned compiler version, and that compiler is still changing.
