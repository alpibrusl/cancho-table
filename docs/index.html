A deterministic data primitive for AI agents.

Query CSV and TSV data with explicit semantics, bounded resources, structured refusals, and machine-verifiable capabilities.

Ask a CSV a question, get an exact answer: with a command line and flags, not a chat box. The same tool for a person and for an agent.

Why table?

Most data tools optimise for flexibility. table optimises for predictability.

  • Explicit typesA column is text unless you write :int (an exact 64-bit integer), :dec(S) (an exact decimal with S fractional digits) or :float (the nearest double, in --where and in every aggregate); a cell that is not one is refused. docs/filter.md
  • Explicit operationsOne plan from flags, resolved against the header before any row is read. No expressions, no functions. docs/filter.md
  • Bounded resource useRows, line and record size, groups, distinct values and group state each have a limit with its own rule (the limits). Peak memory was about 2 MB on a 31.7 MB file (Linux) and 1.6 to 1.8 MB on a 1 GB file (Mac, one core). Benchmarks
  • No implicit network accessThe authority row below lists what the program can reach: no net_out, net_in, ffi or clock, and nothing written to disk. cancho authority derives it, and CI fails if the binary differs from the committed manifest. docs/architecture.md
  • Machine-readable errorsOne JSON line against a schema (table.v2). A refusal is {code, rule, message, hint, repair, detail}. docs/refusals.md
  • Repair hintsA refusal says how to fix the request: a command to run, a choice of commands, or why there is none. docs/refusals.md
  • Capability introspectiontable introspect prints the flags, limits, rules and authority; table skill prints a guide for an agent. Excerpts below
  • The same bytes on any number of cores--threads N gives the one-core answer, the same refusal included. docs/parallel.md

Pick some columns

Name them; they come out in the order you give. A comma inside a quoted field stays inside it, and the output is quoted again.

$ table --select customer,bytes --format csv orders.csv
customer,bytes
"Doe, Jane",512
Acme,
"Doe, Jane",2048
Acme,128
Zed,64

Keep the rows that match

Text compares byte by byte; :int compares whole numbers exactly. Conditions run left to right and stop at the first false one, so the first one here keeps the empty cell away from the number test.

$ table --where "bytes != '' and bytes:int > 100" --select id,customer --format csv orders.csv
id,customer
1,"Doe, Jane"
3,"Doe, Jane"
4,Acme

Filter on decimals

price:dec(2) reads the column as exact decimals with two fractional digits: 12.5 and 12.50 are one value, and the literal is read at the same scale. A cell with more digits than the scale is refused, never rounded, and the repair is the command with the scale the column needs. This example uses a small prices.csv.

$ table --where "price:dec(2) >= 12.50" --format csv prices.csv
item,category,price
book,office,12.50
lamp,home,12.5
$ table --where "price:dec(1) >= 12.5" prices.csv
{"rule": "value.decimal-scale", "hint": "declare a larger scale, :dec(N) with N the most fractional digits the column holds", "repair": {"kind": "choose", "options": [{"argv": ["table", "--where", "price:dec(2) >= 12.5", "prices.csv"]}]}}

Filter and find the extremes of floats

temp:float reads the column as the nearest double (ties to even), and compares doubles, not text: 21.5, 21.50 and 2.15e1 are one value. min and max print as the shortest decimal that reads back to the same double; rows are copied as they are. NaN, inf, an out-of-range number and a cell that is not a number are refused, never skipped, with the row, line and column; for NaN the hint is the idiom that keeps those rows out (temp != 'NaN' and temp:float >= 21.5), and there is no repair, because what the cell was meant to be is not known. min, max, distinct, count, sum and mean work on floats. A column really named x:float is written x\:float.

$ table --where "temp != 'NaN' and temp:float >= 21.5" --format csv readings.csv
sensor,temp
a,21.5
c,21.50
d,2.15e1
$ table --where "temp != 'NaN'" --agg "min:temp:float,max:temp:float,distinct:temp:float" --format csv readings.csv
min:temp,max:temp,distinct:temp
-3.4,21.5,3
$ table --where "temp:float >= 21.5" readings.csv
{"rule": "value.not-finite", "hint": "keep them out with --where first: x != 'NaN' and x:float > 5 never reads the NaN cell as a number", "repair": {"kind": "none", "reason": "what the cell was meant to be is not known"}, "detail": {"path": "readings.csv", "context": "where", "column": "temp", "row": 6, "line": 7, "value": "NaN", "value_truncated": false}}

Sum and average floats, exactly

sum:x:float and mean:x:float are exact: every cell is added without rounding and the total is rounded once to the nearest double (ties to even), so the answer does not depend on the order of the rows or on the number of cores. Adding the same numbers left to right in double precision gives 0.0 for group a and 0.9999999999999999 for group h. A mean takes no @N (it is a double; mean:x:float@2 is refused). A sum beyond the largest double, about 1.8e308, is agg.float-overflow, which names the group; the mean of that group still exists. On a million rows DuckDB's DOUBLE sum gave a different answer at 1, 4 and 16 threads, none equal to the exact one: see the benchmarks.

$ table --group g --agg "sum:x:float,mean:x:float" --format csv drift.csv
g,sum:x,mean:x
a,2.0,0.5
h,1.0,0.1
$ table --group g --agg sum:x:float big.csv
{"rule": "agg.float-overflow", "hint": "sum fewer rows with --where, group by more columns, or sum in a smaller unit (the mean of the same group is a number: mean:COL:float)", "repair": {"kind": "none", "reason": "which rows to leave out is not known"}, "detail": {"path": "big.csv", "context": "sum", "column": "x", "group": "a", "group_truncated": false}}

Sum and average decimals

sum:price:dec(2) is exact and printed at the column's scale. mean:price:dec(2)@3 is the exact quotient rounded half to even at three digits (@N is required for a whole-number column), the same on any number of cores. distinct counts by value, so 12.5 and 12.50 are one. Sums are exact at any width. A column whose name really ends in :int, :dec(2) or @2 is written with a backslash: sum:x\:dec(2).

$ table --group category --agg "sum:price:dec(2),mean:price:dec(2)@3" --format csv prices.csv
category,sum:price,mean:price
home,15.70,7.850
office,14.00,7.000
$ table --agg "min:price:dec(2),max:price:dec(2),distinct:price:dec(2)" --format csv prices.csv
min:price,max:price,distinct:price
1.50,12.50,3

Group and sort by numbers

--group and --order-by take the same suffixes as --where: :int, :dec(S) and :float. The key is the value of the cell, not its text. Here 1.5, 1.50, 01.5 and +1.5 are one group at :dec(2), written back at the column's scale, where grouping by text gives four groups for them. Groups come out in numeric order, and --order-by -price:dec(2) puts 12.50 before 3.2, where a text sort puts 3.2 first; rows that tie keep their order in the file. On a million rows with a number written in two spellings (20,001 values), csvtk and Miller grouped by text and reported 22,002 groups: see the benchmarks.

$ table --group level --agg count --format csv spell.csv
level,count
+1.5,1
01.5,1
1.5,1
1.50,1
2.25,1
$ table --group "level:dec(2)" --agg count --format csv spell.csv
level,count
1.50,4
2.25,1
$ table --order-by -price --limit 3 --select item,price --format csv prices.csv
item,price
cup,3.2
book,12.50
lamp,12.5
$ table --order-by "-price:dec(2)" --limit 3 --select item,price --format csv prices.csv
item,price
book,12.50
lamp,12.5
cup,3.2

Check what is in a column

--report types reads the file once and prints, for each column, how many cells are empty, whole numbers, decimals, floats or something else, the widest decimal scale, the first row and line that each declaration would refuse, and a suggested declaration: :int, :dec(S), :float, or none when a cell is not a number. It prefers the exact reading: a column of 0.1-shaped cells is :dec(1), not :float. It never changes anything; no other flag reads a column as a type unless you write the suffix, and the report is the same on any number of cores. Here price has an n/a in its last row (suggestion none, first offender row 4, line 5), bytes has a 1e3 (:float, not :int) and cents has an empty cell (still :int; the empty cell is counted apart and refused by any numeric reading). On a million rows with three late wrong cells, DuckDB's type sniffing, which looks at a sample of 20,480 rows, still said DOUBLE and BIGINT, and its SUMMARIZE failed at line 900,001; Miller's summary showed the mixtures without counts or rows (benchmarks).

Sort rows

--order-by takes keys: - before a name is descending, :int compares whole numbers, and rows that tie keep their order in the file. With --limit or --top it keeps only the best rows, so memory stays flat. A full sort holds every row, up to --max-sort-rows (1,000,000 by default); past that it refuses and suggests --top, a smaller --limit or a --where. There is no sort that spills to disk.

$ table --where "bytes != ''" --order-by -bytes:int,status --limit 3 --select id,customer,bytes --format csv orders.csv
id,customer,bytes
3,"Doe, Jane",2048
1,"Doe, Jane",512
4,Acme,128

Count and sum by a key

count, sum, min, max, mean and distinct, of whole numbers and of :dec(S) columns, sorted by what you ask for. Sums are exact at any width: a sum past 64 bits is printed in full (up to 28 digits), and it is the same on any number of cores.

$ table --where "bytes != ''" --group customer --agg count,sum:bytes --sort -sum:bytes --format csv orders.csv
customer,count,sum:bytes
"Doe, Jane",2,2560
Acme,1,128
Zed,1,64

Join two files

--join FILE --on PROBE=BUILD joins the file you name (or standard input) with a second one. The operand is the probe side and is streamed; the --join file is the build side and is held whole in memory, counted in --max-state-bytes. --join-type is inner (the default: each probe row, in the probe's order, once for every build row with its key, in the build's order, followed by that row's cells), left (the same, and a probe row with no match once, with every cell of the build row empty: there is no null), semi (each probe row that has a match, once, with its own cells) or anti (each probe row that has none, once). A key is compared as text, byte for byte (007 is not 7, and an empty cell matches an empty cell: there is no null), or as a number when the pair ends in a type, --on id=user:int (also :dec(S) and :float): then 007 is 7, -0 is 0, 1.5 is 1.50, and a cell that is not of the type, an empty one included, is refused. --on a=x,b=y is a key of two pairs (up to eight); --on id names a column both files have, and the answer shows it once. Two files that share a column name are refused as join.column-collision, and the refusal offers the invocation with a --join-prefix. A number read from a padded cell of a left join is refused as any empty cell is, and the refusal says padded.

$ table --join customers.csv --on customer=name --join-prefix c_ --select id,customer,bytes,c_tier --format csv orders.csv

2,Acme,,silver

4,Acme,128,silver
4,Acme,128,reseller
5,Zed,64,bronze

Ask in a small SQL

--query takes one statement of a small subset of SQL (select, from, where with and, group by, order by, limit, offset) and means exactly the flags it is translated to: one plan, the same bytes. What the subset leaves out (or, aliases, expressions, like, null, joins) is refused with the feature named and what to write instead; a mistake is refused at its byte, with a corrected command when the correction is certain.

$ table --query "select customer, count(*), sum(bytes) from 'orders.csv' where bytes != '' group by customer order by sum(bytes) desc limit 2" --format csv
customer,count,sum:bytes
"Doe, Jane",2,2560
Acme,1,128
$ table --query "select customer form 'orders.csv'"

See the plan before it runs

--explain takes the flags (or the --query) of a call and prints, as one JSON line, what the call would do, without doing it: each column the plan names and where the header puts it, every condition, group, aggregate and order with the type it is read as, the page, the kind of work it is and the limits in force, how many threads it would use and why not more, the rules the data could still refuse it with, and notes. It reads the first 64 KiB of the file for the header and nothing after the header, so what it costs does not grow with the file; it does not read standard input at all. A plan the run would refuse before it read a row is refused with the run's own error and exit status.

$ table --explain --threads 4 --where "bytes:int > 100" --group customer --agg count,sum:bytes --sort -sum:bytes --limit 2 orders.csv

Get CSV back

--format csv writes the rows as CSV as they are read, whatever the file size. Every column when you do not pick any. A non-zero exit means the output is only the start of the answer.

$ table --where "status = 200" --format csv orders.csv
id,customer,status,bytes
1,"Doe, Jane",200,512
3,"Doe, Jane",200,2048
5,Zed,200,64

Use several cores

--threads N reads the file with N cores (1 to 64). The answer is the same bytes as with one core, refusals included. Files under 1 MiB are read on one core whatever you ask, so this tiny example only shows the same answer.

$ table --threads 4 --group status --agg count --format csv orders.csv
status,count
200,3
404,1
500,1

What it cannot do yet

  • Numbers are mostly built. :int, :dec(S) and :float work in --where, --agg, --group and --order-by. Columns of 15- to 17-digit numbers are read by an exact reader that allocates nothing on the paths a real column takes (Clinger, then Eisel-Lemire, then an exact fallback); it matched Python’s float() on every cell of a differential run of over 100 million cells, and takes 29.6 ns a cell against 1,151 ns before (one Mac core, load 6.7 to 13.5). Conditions.
  • A sort uses more cores only for a whole sort written as CSV. With --order-by, --format csv and no --top, --limit or --from, --threads above 1 sorts in parallel and gives the same bytes; pages, --top and JSON output run on one core. A threaded sort needs several times the memory of the sequential one. There is no sort that spills to disk.
  • One join, in two slices of it: --join FILE --on KEYS joins the operand (or standard input) with a second file, as an inner, left, semi or anti join, on up to eight pairs of columns, each compared as text or, with a type (:int, :dec(S), :float), as a number, giving rows. No right or full join, no --group, --agg, --order-by or --report over a join (write the join as csv and pipe it into a second call), no filter that runs before the key is read (a typed key is refused at the first cell that is not of its type), no --query with a join. The --join file is held whole in memory, counted in --max-state-bytes (resident memory can be up to about three times that while it grows), and nothing spills to disk. A join is read on one core whatever --threads says (docs/joins.md).
  • One input at a time otherwise: a file named on the command line, or standard input (-, or no file), read in one pass on one core, in blocks, at about the speed of a named file on one core. A producer that writes slowly is waited for until the first 512 bytes arrive; a closed descriptor 0 reads as empty; a descriptor that fails is refused with an io.* rule (docs/readers.md 11.1, 11.7).
  • JSON lines are read (--input-format jsonl, columns declared with --fields), and written (--format jsonl: one object per row, keys the output columns, every value a string but the aggregates); nothing else: no Parquet, no JSON array. CSV and TSV (comma, tab or semicolon) as before. Reader design and build: docs/readers.md, section 12.
  • --query is a small subset of SQL, not SQL: no or and no parentheses, no aliases, no expressions or functions, no like, no null, no joins, no subqueries, and a grouping sorts by one column. Each is refused as query.unsupported, with the feature named (docs/query.md).
  • No guessing. Every column is text unless you declare :int, :dec(S) or :float; --report types suggests a declaration and applies none. No computed or renamed column, no or in a filter.

or in a filter and the rest of joins are on the backlog, in rough order. Nothing there is promised.

Quick start

You need Rust, git, clang and Python 3. On a 16-core Mac with Rust installed and its dependencies already downloaded, the compiler built in 19 seconds and table in 3. The clones and a first-time dependency download are extra: allow a few minutes the first time.

git clone https://github.com/alpibrusl/cancho
git clone https://github.com/alpibrusl/cancho-table && cd cancho-table
REV=$(sed -n 's/^cancho *= *"\([0-9a-f]*\)".*/\1/p' cancho.toml)
(cd ../cancho && git fetch -q origin && git checkout "$REV" && cargo build --release -p cancho)
export PATH=$PWD/../cancho/target/release:$PWD/build:$PATH
cancho build                       # builds build/table

cat > orders.csv <<'EOF'
id,customer,status,bytes
1,"Doe, Jane",200,512
2,Acme,404,
3,"Doe, Jane",200,2048
4,Acme,500,128
5,Zed,200,64
EOF

Built in cancho, with an authority the compiler wrote

cancho is a language whose compiler writes down what a program may do (cancho authority). For table that is the line below: it can read its arguments, the file (or standard input), allocate memory, start threads and write to the terminal. It cannot use the network, call foreign code, read the clock or write a file. CI fails if the binary says otherwise. Why each label is there, and what a row cannot say: docs/architecture.md.

How fast

Supporting evidence, not the point: predictability costs little speed. A core is one of the independent workers inside a processor; table uses one by default and --threads 16 uses sixteen. DuckDB is a full database engine and a popular, fast way to query a CSV, so it is a fair yardstick. On these four questions one core of table is about as fast as, or faster than, DuckDB on all sixteen. With many distinct keys in a group-by, the answer depends on which DuckDB time you compare with (see below).

Filtering on a decimal column (price:dec(2) >= 500.00) costs up to about 10 percent more than on a whole-number column: 0.070 s on one Mac core for 1,000,000 rows, against 0.186 s for DuckDB on one core. Summing and averaging a decimal column by a key takes 0.085 s on one Mac core, 2.5 times faster than DuckDB; DuckDB’s floating-point sum gave different, slightly wrong answers at one and at sixteen threads, while table’s exact sum did not change. Filtering a float column with two decimals is 2.9 times faster than DuckDB’s DOUBLE on one Mac core; a column of 17-digit numbers was the exception before the new reader, when min and max took 1.09 s against DuckDB’s 0.208 s. Summing a float column exactly is 2.3 times faster than DuckDB’s inexact DOUBLE sum on one Mac core (6.0 times on 16). On a column of 17-digit numbers it was 5.7 to 24 times slower until the reader was replaced (#32); with the new reader the same kind of question over a 17-digit column takes 0.112 s on one Mac thread against DuckDB’s 0.230 s, and 0.021 s on 16 against 0.088 s (shared Mac, load average 15.9 to 25.6, minimum of 7; conditions). Grouping by a float column takes 0.181 s on one Mac core, level with DuckDB (0.167 s), and csvtk and Miller get the group count wrong. The type report is a full read: 0.273 s on one Mac core, 0.038 s on 16, against DuckDB’s sampling DESCRIBE at 0.059 s (4.6 times faster than table on one core). The numbers. Typed keys.

On the Linux machine (six threads on three physical cores) the four questions go the same way: table on one thread is level with or ahead of DuckDB on six (filter 0.072 s against 0.104 s, pick 2 columns 0.087 s against 0.151 s, count by a key 0.094 s against 0.107 s, sum by a key 0.112 s against 0.112 s; 1,000,000 rows, 31.7 MB, minimum of 5 runs, load about 5, cores 0–5), and, in the runs that measured it, DuckDB was ahead on sorting whole files and on groupings with a million keys; the threaded sort and group-by since merged narrow that, with costs (below). The Linux numbers.

Where it is slower, and what it costs

  • A group-by with many distinct keys, against DuckDB’s unsorted time. On Linux at 6 threads (three physical cores, load average 1.1 to 1.4, minimum of 5, 1,000,000 rows) table takes 1.77 and 1.86 times DuckDB’s unsorted time for a count and a sum over 1,000,000 keys, and 1.46 times for distinct over unique values; it takes 1.10 and 1.07 times at 100,000 keys (count and sum). Against DuckDB’s time when its groups are also sorted by the key, which is what table returns, it is level on the million-key count and sum (1.00 and 1.01 times). On the Mac at 16 threads it is ahead of DuckDB’s unsorted time on all five cases (0.35 to 0.52 of its time). Before the change (#35) it was 3.4 times slower than DuckDB on one Mac core on the million-key count and 9.4 times slower than DuckDB on 16. Table and conditions.
  • Sorting rows. A whole sort written as CSV with --threads 16 takes 0.064 s on a text key and 0.053 s on a whole number (1,000,000 rows of 40 bytes, Mac, load average 6.6 to 8.4, minimum of 5), against DuckDB’s default at 0.139 s and 0.120 s. On Linux at 6 threads it is level with DuckDB on one key (0.287 s against 0.293 s) and behind it on two keys (0.459 s against 0.385 s). Pages, --top and JSON output still sort on one core. Table and conditions.
  • Memory costs. A threaded sort peaks at 11.8 to 14.8 times the 39.55 MB file at 16 threads on the Mac (466 to 585 MB), against 4.4 to 6.2 times for the sequential sort. A threaded grouping that is then refused peaks higher than before: 325 to 471 MB at one byte short of the limit and 181 to 360 MB with --max-state-bytes at 2,000,000 (the million-key count, B3, Mac, 16 threads). --max-state-bytes counts accounted bytes, not resident memory. Non-group cells at 4 threads retire 0.8 to 0.9 percent more instructions on the Mac.
