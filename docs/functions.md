# Functions in `--compute`: a design (slices K5 to K8)

> **Status: design; K5a (`--explain` for the stage, section 3.1), K5 (the numeric functions, section 3.2) and K6 (the text functions, section 3.3), K7a (conditions on numbers, section 3.4) K8a (the date functions that give numbers) and K8b (`add_days`, section 3.5) are built; K7b1 (a comparison of texts in a condition) and K7b2 (an `if` that gives a text, section 3.4) are built, K7b2 narrower than first designed.** Every claim is a **choice**, a **read** (file), **measured** (with the command), or **open**. A measurement replaces its line, in place, when it exists.
> Written 2026-11-15 after the maintainer's direction (relayed in the working session): *unblock functions without affecting performance or the first principles.*
> It amends item 14 of `docs/backlog.md` (the decision of 2026-11-09) and reopens two lines of `docs/computed-columns.md` section 10 ("Rounding functions: out", "Dates: out"); both are corrected in place and point here.

## 0. The decision, and what it keeps

**Amended rule (choice, the maintainer's).** A *derived column* is in `table`; an *in-place rewrite* is out. `--compute` already only appends columns (`compute.duplicate-name` refuses a name that is an input header, `docs/computed-columns.md` section 3), so a function that makes a new column from old ones is a derivation. `--lower COL`, `--clip`, `--sentinel` as a value rewrite and `--dedupe` stay out, as item 14 says.

Item 14 gave three reasons for putting transforms in another tool. Each is answered here, not argued away:

| reason of 2026-11-09 | answer |
|---|---|
| `--query` has no expressions or functions | it still has none. A function is a flag of the stage; a `--query` that wants one is `query.unsupported`, naming the flag form (as `--compute` is refused beside `--query` today, `docs/computed-columns.md` section 4) |
| `--explain` and the equivalence gates assume one plan from flags or query | the stage has **one plan form**, and it gets an `--explain` (K5a below) and an oracle gate (G-FN-ORACLE). **Measured gap:** `table --compute 't=a:int*b:int' --explain f.csv` is today `compute.unsupported-combination` (one run, `table` built from this repository's `main` at `a553449` with the pinned compiler, 15 Nov 2026; the refusal's `detail.flags` lists `--compute --select --where --group --agg --order-by --report --rows --join --query --sort --top --rename`), so the stage has no explain yet; closing it comes first |
| a transform changes the data the plan is about | a derivation does not: the input columns are written as they were read, byte for byte, then the new ones |

## 1. Invariants every function keeps (the first principles, as gates)

1. **Typed, no coercion.** A function has a signature (argument kinds, result kind). A mismatch is `compute.type-mismatch` with a repair. Nothing is converted silently: a text is never read as a number inside a function, as a column is never read as one outside `:int`/`:dec(S)`.
2. **Bounded.** Every function declares its output bound. A result that would pass the record limit (`--max-line-bytes`) is `compute.result-too-long`, never truncated. At most 8 definitions, 4 levels of nesting, 8 arguments (the first two are the existing limits' neighbours: **choice**).
3. **Deterministic and local.** No locale, no `now`, no zone database, no random, no I/O. Case mapping is explicit (section 3). The same bytes on any number of cores: the stage is one loop on one core (as `--compute` is), so there is nothing to merge.
4. **A refusal names the definition, the column and the row, never the cell** (the rule of `--compute`).
5. **The existing paths do not change.** A function lives in the stage's loop and in no other. `--where`, `--query`, `--group`, `--agg`, `--join` take no function (**choice**: their docs say "no expressions, no functions", and a function there is the select path's 1.01 budget, `docs/or-and-columns.md` 8.3). The idiom is two stages.

## 2. Two value domains, so the exact machine stays as it is (choice)

`tools/table/cexpr.cho` (775 lines) is an integer stack machine over the 180-bit core of `tools/table/cmpv.cho` (**read**): opcodes cell, const, add, sub, mul, div, neg. A text has no place in it. So:

* A definition has **one result kind**: a number (`int` or `dec(S)`, the existing machine) or a text (a new, small evaluator over byte slices of the row copy and one scratch arena).
* **Numbers keep their machine, untouched.** A number-valued function that takes numbers (`abs`, `round`) is an opcode (`op_fn`) with the function's id in `b`. A number-valued function of a text or a date (`len(s)`, `year(d)`) is a **leaf**: it produces an integer that is pushed as an operand, so the arithmetic around it is unchanged.
* **Texts have their own grammar**: `fn(text_operand, literal ...)` nested to 4 levels, no arithmetic. A column is a text operand as itself (`name`); a date operand is `d:date` as in `--where`.
* **No automatic conversion between the domains** (invariant 1). Whether a number may be written as text (`text(x)`, exact, at its scale) is **open** (section 7).

## 3. The functions, by slice (each a row of the signature table)

The signature table is **one static table** that the parser, `introspect`, the skill text and the MCP schema all read (as the lexical tables of `docs/query.md` section 10 are), so the surface is generated, not written twice. **Names must not be a reserved word of `--query`** (`count sum min max mean`, `docs/query.md`), hence `greatest`/`least`.

### 3.1 K5a: the explain document of a stage (built 2026-11-15)

> **Status: built.** The text below is the design as first written, **corrected in place** where the build differs: the stage is an **additive member** (`stage`) of the one explain document, and `plan` stays the plan of the read, so every consumer of the existing keys keeps working and the explain of every other plan is the earlier bytes.

**Read** (`table --rows --explain f.csv`, `table --group s --agg count --explain f.csv`, 15 Nov 2026, `table` built from `main` at `a553449`): an explained plan is one document `{"explain": {...}}` with the keys `source`, `plan`, `output`, `work`, `refusals`, `notes`, `sql`, `sql_flags`. **The refusal that was there** was one name (`inp.has_explain`) in the list that `--compute` refuses in `tools/table/table.cho`; it is removed.

| key | for `--compute 'NAME=EXPR;...'` (as built) |
|---|---|
| `source` | as for any plan (the header is read, nothing else) |
| `plan` | **unchanged**: the plan of the read (`form: "rows"`, every column, no condition, `limit`, `from`) |
| **`stage`** (new, only for a stage whose header is known) | `{"definitions": [{"name": "t", "scale": 2, "instructions": 3}, ...], "max_definitions": 8}`: the names, scales and program sizes are the compiler's (`cexpr.compile`, `cexpr.scale_of`, `cexpr.size_of`), not a guess. **Corrected:** the first design also had a `kind` (`int` or `dec`); the machine has no such distinction in a result (a scale of 0 prints as an integer), so there is none |
| `output.columns` | every input column, then every name: the header of the real answer |
| `work` | the read's; `threads.effective` is **1** and `reason` is `the --compute stage runs on one core`, whatever `--threads` says (found while building: the first version said `effective: 4` on a large file, which the stage never does; `test_the_stage_runs_on_one_core_whatever_threads_say`) |
| `refusals.possible` | the I/O and reader rules of any plan, then exactly those that this program can give: `value.not-integer` and `value.integer-overflow` if a cell is read as `:int`, `value.not-decimal`, `value.decimal-scale` and `value.decimal-too-wide` if a cell is read as `:dec(S)`, `compute.overflow` if any definition has an operator, `compute.divide-by-zero` only if one has a `/` |
| `sql`, `sql_flags` | `null` and `[]`, with the note `sql.compute: no query is shown for this plan: --compute adds columns that a query has no word for` (a new reason, `qsql` code 11) |

**A definition that does not compile is the explain's refusal**, with the rule, message and detail the run gives (`compute.syntax`, `compute.unknown-column`, `compute.too-long`, ...). A constant zero divisor (`t/0@2`) **does** compile: it is a refusal of the data, so it is in `refusals.possible` and not a certain refusal. The explain reads the header and runs no row. **Not resolved:** for standard input the header is unknown, so there is no `stage` member and the existing note says so (`test_standard_input_is_not_read`).

**Gates** (`tests/conformance/test_compute_explain.py`, 11 tests; `scripts/compute_explain_mutants.py`, 17 mutants):

* *G-EXPLAIN-CERTAIN*: 20 definitions that do not compile; the explain's `error`, `errors`, message and exit status equal the run's.
* *G-EXPLAIN-PLAN*: six valid stages (a product, a division at a scale, a chain, a quoted name, unary minus); `stage.definitions` equal the names written by the run after the input columns and the fractional digits of its values, and `output.columns` is the run's CSV header.
* *G-EXPLAIN-POSSIBLE*: eight hostile files (a bad integer, an integer past 64 bits, a bad decimal, too many fractional digits, too wide a decimal, an overflow, a zero divisor, a ragged row): the rule the run gives is in the list; and a rule that the definitions cannot reach is not in it.
* *G-EXPLAIN-NOREAD*: a 3 MB file whose rows are all garbage explains, and `bytes_read` is the header chunk's, under 70,000.
* *G-COMPAT*: the explain of every other plan is the earlier one: `test_explain.py` (42 tests) and `test_sql_explain.py` (10) pass unchanged beside the new file.

### 3.2 K5: the numeric functions, exactly (built 2026-11-15)

> **Status: built.** The text is the design as written before the code, **corrected in place** where the build differs (marked *Corrected*); the gates are listed at the end of the section.

**Grammar.** A call is `name(` argument { `,` argument } `)` with the `(` **immediately** after the name (no space). A word followed by `(` is a call; a word followed by `:` or by anything else is a column or an earlier definition, as today, so a column called `abs` is still `abs:int`. A call is an operand: it can be anywhere an operand can, inside an operator expression and inside another call. **Choice:** a call's parenthesis counts as one of the 4 levels of `compute.too-long`, its arguments are pending operands (the limit of 10), and a call has at most 8 arguments.

| function | arguments | result scale | meaning (exact; Python integers are the reference) |
|---|---|---|---|
| `abs(x)` | 1 | scale of `x` | the magnitude |
| `sign(x)` | 1 | 0 | -1, 0 or 1 |
| `greatest(a, b ...)`, `least(a, b ...)` | 2 to 8 | the largest scale among the arguments | each argument is rescaled **exactly** to the result scale, then compared; a rescale that leaves 127 bits is `compute.overflow` |
| `round(x, n)` | 2: `x`, and `n` an **integer literal 0 to 18** | `n` | `x` at scale `n`, ties **to even** (the rule of `/ @N`) |
| `floor(x, n)` | the same | `n` | toward minus infinity |
| `ceil(x, n)` | the same | `n` | toward plus infinity |
| `trunc(x, n)` | the same | `n` | toward zero |
| `coalesce(c, lit)` | 2: `c` a **plain typed column** (`price:dec(2)`, `qty:int`), `lit` a number with an optional `-` | the scale of `c` | `lit` (scaled to the scale of `c`) when the cell of `c` is **empty**, else the cell exactly as `c:type` reads it; any other bad cell is still its `value.*` refusal |

* If `n` is not below the scale of `x`, `round` and its kin only add zeros: `x * 10^(n - scale)`, `compute.overflow` past 127 bits. Below it, the digits dropped are decided by the rule of the function.
* **An empty cell** is a cell of zero bytes (a quoted `""` too). A cell of spaces is not empty; it is refused as it is today.
* `coalesce` takes a *column*, not an expression, because the empty cell is a fact of a cell and not of a value: `coalesce(price:dec(2) * 2, 0)` is `compute.syntax` at the first argument. A literal with more fractional digits than the column's scale is `compute.bad-literal`.
* **No float anywhere**; a `:float` operand is still `compute.float-operand`.

**New refusals** (exit 2, as the other `compute.*` compile refusals; no payload): `compute.unknown-function` (status 13: the name is not in the table; *Corrected:* the hint lists the names, there is no `detail.available`), `compute.arity` (status 14: too few or too many arguments, at the name), `compute.bad-literal` (status 15: the scale of `round` and its kin is not an integer literal 0 to 18, or the literal of `coalesce` is not a number or has more fractional digits than the column). `compute.syntax` stays for a comma outside a call, an empty argument, or `coalesce` of a non-column.

**Encoding (choice, nothing at run time beyond the machine).** A call is postfix: its arguments' instructions, then `op_fn` with `a` the function id, `b` the number of **operands it takes off the stack** (for the rounding family one: the scale is not an operand; *Corrected:* the first build counted it, and the first run trapped) and `c` the literal `n` of the rounding family. A `coalesce` is the cell instruction with its kind raised by 2 (`2` an integer, `3` a decimal with a default) followed by an `op_const` that the evaluator reads as the default and skips; so a cell instruction is the same four ints it is. `shape` (scale and pending depth) reads `op_fn` as "pop `b`, push one".

**The reference** is `scripts/cexpr_golden.py`: the tree of Python integers gains a `fn` node and a `coal` node (the code is the table above, and the rounding family is also checked against Python's `decimal` module, which shares no code with either: `scripts/cexpr_golden.py --selftest`). **Gates:** G-FN-ORACLE for the numbers (random calls, nested, with the operators, at all scales, with ties and values near 2^127), G-FN-MUT (below), `tests/conformance/test_compute.py` through the binary, and the explain's `refusals.possible` (a call that can overflow lists `compute.overflow`).

**Gates, as run** (compiler `119bcfe`, 15 Nov 2026):

* *G-FN-ORACLE* (`scripts/cexpr_golden.py`): the reference of Python integers gains the calls; **5,256 cases, 0 differences** at two seeds (about 3,000 random expressions with calls nested up to the four levels, 600 `coalesce` cases with the cell empty or not, the 1,500 chains of K4, and 133 hand cases for every value and every refusal of the table), and **3,000 fuzz cases with no trap**. The rounding family of the reference is itself checked against Python's `decimal` module (`--selftest`: 200,000 cases with ties on purpose, four modes, 0 differences). The probe also says, for every definition, whether the scale it was compiled with is the scale of the value it computed (`S definition compiled computed`): that check found nothing in the older features and is what kills the mutant that corrupts the compile-time scale of a `coalesce`.
* *G-FN-MUT* (`python3 scripts/cexpr_golden.py --mutants`): 29 mutants of the calls and of the exact core's new functions beside the 25 earlier ones; the first run killed 53 of 54, and the survivor (the compile-time scale of a `coalesce`, which only the explain showed) is what the probe's scale check was added for.
* *Through the binary* (`tests/conformance/test_compute.py`, `Functions`, 8 tests, and the random trees of `Compute`, which now draw calls): the values in CSV, `greatest` and `least` across scales, `coalesce` of an empty cell and of a bad one, JSON lines with `--absent empty`, the three new rules with their exit status and offset, overflow as a refusal, and a function name that is still a column name.
* *Explain* (`test_compute_explain.py`): a call that can overflow lists `compute.overflow` and `abs` and `sign` do not; `coalesce` adds no rule beyond its cell's; the scale of a call is in `stage.definitions`; a call that does not compile is refused as the run refuses it.

**Not measured:** the cost of a call (G-COST). No speed is claimed for the functions; the baseline of section 5 stands.

### 3.3 K6: the text functions, exactly (built 2026-11-15)

> **Status: built.** The decisions that show in a definition (the string literal, ASCII case, bytes, what `len` takes) were **choices**, confirmed by the maintainer as written ("go as written", 2026-11-15). The text below is the design as written before the code, **corrected in place** where the build differs (marked *Corrected*); the gates are at the end.

**Two kinds of definition.** A definition is **text-valued** when its expression is a call of a text function (`lower`, `upper`, `trim`, `ltrim`, `rtrim`, `substr`, `concat`, `replace`), and **number-valued** otherwise (everything of K5, plus `len`). A text-valued definition has no operators: its expression is one call whose arguments are text operands, which are themselves calls. A number-valued one never takes a text except as the argument of `len`. **No automatic conversion** either way: `lower(price:dec(2))`, `upper(1)` and `1 + lower(name)` are `compute.type-mismatch`.

**Text operands.** A **column without a type** (`name`, `#3`, `'my col'`: the cell as text, exactly its bytes, a quoted cell with its doubled quotes undone), a **string literal** in **double quotes** (`"abc"`; `""` inside is one quote; no other escape; the bytes as written), or a call. **Choice:** a literal is in double quotes because single quotes already name a column (`'my col'`), and a column called `abc` must stay `abc` or `'abc'`.

| function | arguments | meaning (bytes; Python's `bytes` methods are the reference) |
|---|---|---|
| `lower(s)`, `upper(s)` | 1 | the 26 ASCII letters changed; **every other byte unchanged** (no locale, no Unicode tables: `lower("Ã")` is `Ã`) |
| `trim(s)`, `ltrim(s)`, `rtrim(s)` | 1 | ASCII space (0x20) and tab (0x09) removed from both ends, the left, the right |
| `substr(s, start, count)` | 3: `start` an integer literal from 1, `count` an integer literal from 0 (digits only, **at most nine of them**: *Corrected:* a tenth digit is `compute.bad-literal`, as the two are packed into one instruction) | the bytes from `start` (1 is the first), at most `count`, clipped to the end; a `start` past the end is empty. A cut **between a byte and a continuation byte** (0x80 to 0xBF) is `compute.not-utf8-boundary` for that row: a half character is not a text |
| `concat(a, b ...)` | 2 to 8 text operands | the bytes one after the other |
| `replace(s, from, to)` | 3: `from` a **non-empty** string literal, `to` a string literal | every non-overlapping `from`, left to right (`replace("aaa","aa","b")` is `ba`) |
| `len(s)` | 1: **a column without a type or a string literal** (*Corrected:* a typed column, a call and the name of an earlier definition are each `compute.type-mismatch`) | the **number of bytes**, an integer (scale 0). Number-valued: `n=len(name)+1` is an expression of K5. **Choice:** its argument is not a call in this slice |

**What a text result is.** A text of any bytes. It is written into the answer **as a quoted cell** (the quotes inside doubled, flagged as the reader flags a cell it read quoted), so the writers quote it when it has to be (`csv_cell` quotes an unquoted cell only for a quote or a CR, because a field read from a file cannot hold a delimiter or a line feed, which a computed text can; **read**: `tools/table/writer.cho`, `csv_cell`) and JSON writes it as a string (`json_cell`). The row's line is longer by its length, so a result that would take the record past `--max-line-bytes` is `compute.result-too-long` for that row (never truncated). *Corrected:* an **intermediate** text longer than `--max-line-bytes` (a `replace` that grows it, a cell that is itself longer) is refused the same way, which keeps the arena to one limit's worth for each value.

**Evaluation.** One new small evaluator for texts, `tools/table/ctext.cho`: a postfix program of the same shape as the number one (`op`, `a`, `b`, `c`), values held in one scratch buffer that is emptied for each row, the cells copied into it unquoted. The number machine (`cexpr.cho`, `cmpv.cho`) is **not changed** except for one leaf, `op_len`, which reads a cell's byte count. Literals are read from the definitions' own text.

**New refusals** (compile ones exit 2 as the others; row ones exit 8): `compute.type-mismatch` (status 16), `compute.result-too-long` (row, 17), `compute.not-utf8-boundary` (row, 18). **Existing and reused:** `compute.unknown-function` and `compute.arity` as in K5; `compute.bad-literal` for a `start` below 1, a `count` that is not an integer, an empty `from`, and a string literal that is not closed; `compute.syntax` for the rest. The limits are those of K5 (8 definitions, 256 bytes each, 4 levels, 8 arguments); a text definition holds at most 8 calls deep through nesting counted as parenthesis levels.

**Stage and explain.** A text definition is `{"name": "u", "kind": "text", "instructions": N}` (no `scale`); a number one is as before. `refusals.possible` adds `compute.result-too-long` for every text definition, `compute.not-utf8-boundary` if it has a `substr`, and nothing for a text column (a text cell cannot fail to be read).

**The reference** is `scripts/ctext_golden.py` (Python, `bytes`/`str` methods, no code shared with the tool): the same shape as `cexpr_golden.py`, with a probe over `tools/table/ctext.cho`. **Gates:** G-TX-ORACLE (random texts: ASCII, 2- to 4-byte characters, quotes, commas, line feeds, empty; random nested calls; refusals), G-TX-MUT (mutants of the evaluator and of the parser), G-TX-WRITE (through the binary: CSV that a CSV reader reads back to the same fields, and JSON, for texts with a comma, a quote, a line feed and a CR), `compute.*` explain, and `test_compute.py` as for K5.

**Choices, confirmed as written.** (1) The string literal in double quotes. (2) ASCII-only case mapping and bytes for `substr` and `len` (a character count is a different function: **open**). (3) `len` takes a column or a literal, not a call. (4) A text result is a quoted cell. (5) No conversion between texts and numbers in either direction; `text(x)` stays **open**.

**Gates, as run** (compiler `119bcfe`, 15 Nov 2026):

* *G-TX-ORACLE* (`tests/conformance/test_compute_text.py` against `scripts/ctext_ref.py`, Python's `bytes` methods): the hand cases (every function, every refusal, the boundary at the first and the last byte, chaining, `len`), and **6,000 random definitions over random texts** (ASCII, 2 to 4 byte characters, quotes, commas, line feeds, CRs, empty, bytes that are not UTF-8) at three seeds, **0 differences**, the refused rows included (the rule and the row).
* *G-TX-WRITE*: the answer is CSV that a CSV reader reads back to the same fields (a delimiter, a quote, a line feed, a CR in a result), JSON that reads back to the same strings, and the same through JSON lines and standard input.
* *G-TX-MUT* (`python3 scripts/ctext_mutants.py`): 37 mutants of the evaluator, the compiler's text half, the row and the explain.
* The explain (`stage.definitions[].kind: "text"` and no scale; `compute.result-too-long` for a text, `compute.not-utf8-boundary` only with a `substr`), `test_rules` (a fixture for each new rule).

**Found by the gates:** `substr` took three operands off the stack where it has one (the start and the count are literals), a trap on the first run; and my hand case for `substr` over `\x80\x80` expected a value where the rule of the design refuses (the cut is before a continuation byte): the tool was right and the hand case wrong.

**Not measured:** the cost of a text function (G-COST). No speed is claimed.

### 3.4 K7: conditions (design 2026-11-15; K7a built 2026-11-15)

> **Status: K7a, the numbers, is built (the as-built block at the end of this section); K7b, the texts, is not.** Every line is a **choice**, a **read** (file) or **open**. Nothing here was timed.

**The problem it must solve first (reasoned, to be measured by G-IF-LAZY).** The use that justifies K7 is a guard: `if(qty != 0, total / qty, 0)`. A machine that computed both branches and then picked one would refuse `compute.divide-by-zero` on the rows that the guard was written for. So **only the chosen branch is evaluated**, exactly as `--where` evaluates left to right and reads a typed cell only when its condition is reached (**read**: `docs/or-and-columns.md` section 0, row "evaluation"). A bad cell, an overflow or a zero divisor in the branch that is not taken is not an error.

**Surface (choice).**

```
table --compute 'r=if(qty != 0, total / qty, 0);tag=if(name = "", "none", upper(name))' f.csv
```

| part | rule |
|---|---|
| `if(cond, a, b)` | exactly three arguments; the name `if` is a function name of the stage only, it is not a reserved word of `--query` or `--where` (**read**: `docs/query.md`, the reserved words are `count sum min max mean`) |
| `cond` | one comparison `x OP y`, or up to **4** comparisons joined by `and` only, or by `or` only. `OP` is one of `= != < <= > >=`. **No `not`, no parentheses, and `and` mixed with `or` is refused** (`compute.mixed-and-or`, the repair is the nesting, written out for the user: `if(c1 and c2, a, if(c3, a, b))` for one reading, and so on), the rule of `--where` (**read**: `docs/or-and-columns.md` section 3.3): a refusal can become an answer later, an answer cannot become a refusal |
| operands of a comparison | two **numbers** (any expression of K5, compared **exactly** after bringing both to the larger scale, `cmpv.cmp`) or two **texts** (a column without a type, a string literal, a call of K6; compared **bytewise**, the shorter first on a tie). A number against a text is `compute.type-mismatch`; there is no coercion (invariant 1) |
| `a`, `b` | both numbers or both texts (else `compute.type-mismatch`). Numbers: the result scale is the larger of the two, the other is brought to it exactly (an overflow is `compute.overflow`, never a rounding). Either may itself be an `if` (nesting counts as a paren level; the 4-level limit holds) |
| a boolean kind | **none.** A comparison exists only as the condition of an `if`; a definition cannot be a boolean and no column can be written as `true`/`false` (choice: it is the smallest thing that is not a boolean language, as `docs/or-and-columns.md` section 0 chose for `--where`) |
| text `<` `>` | bytes, not a collation: `"B" < "a"` is true. No locale (invariant 3) |

**Evaluation (choice).** The number machine gets **two** new opcodes, a conditional skip and an unconditional skip (`op_jf`, `op_jmp`, forward only, `a` = how many instructions to skip), so a program is still a flat array run once, left to right, with no stack of frames. A comparison of numbers is an instruction pair (the operands, then `op_cmp` with the operator in `b`, leaving a verdict) and `and`/`or` are the short circuit: the first verdict that decides ends the condition (`and`: a false, `or`: a true), as `expr.eval` does. A text-valued `if` is the same program of `ctext.cho` with the same two jumps. The new code is a **new file** (`tools/table/cif.cho`), because `cexpr.cho` is 1,648 lines and the limit is 2,000.

**New refusals.** `compute.mixed-and-or` (compile, exit 2) and `compute.too-many-conditions` (compile, exit 2, more than 4 comparisons in one `if`); `compute.type-mismatch`, `compute.arity`, `compute.syntax` as before. **No new row refusal.**

**Explain.** `stage.definitions[].instructions` counts the jumps; `refusals.possible` is the union of both branches' and the condition's (the explain says what *can* happen, as it does now).

* **The program.** Five new opcodes: `op_cmp` (the operator in `a`), `op_jf`, `op_jt`, `op_jmp` (a skip counted after the jump) and `op_scale` (the value on top, brought to the scale `a`). `if(c1 and c2, A, B)` is `c1 cmp jf(else) c2 cmp jf(else) A scale jmp(end) else: B scale`; an `or` list is `jt(then)` for all but the last comparison. The target of a jump is not known when it is written: it is left as `-1` and patched at the comma that ends the part it jumps over, and `if_close` takes the scales of the two arms with `shape` over each range and writes the larger into both `op_scale`s. A skip is relative, so the instructions of an earlier definition copied into a later one carry their jumps unchanged. `shape` follows the program in one pass: `op_jmp` puts the stack back where the first arm started, so the second arm pushes in its place.
* **The comparison** brings the operand at the smaller scale to the larger by `cmpv.mul_pow10` and compares the two limbs; it cannot overflow (a value is under 2^127, the scales differ by at most 18, the limbs hold 270 bits), so it does not use `rescale`, which refuses 2^127. `op_scale` does use `rescale`: a result that does not fit is `compute.overflow`, as everywhere.
* **The syntax, as it came out.** A comparison operator is read where an operator is read, so `a:int<b:int` needs no spaces (a type, a number or a `)` ends the operand); `and` and `or` are words and need a space or a `)` before them. A comparison operator is only valid directly in the condition of an `if` (anywhere else, `compute.syntax`); `<` where an operand is expected is read as a column name, as `--where` reads it, so `if(< 1, ...)` is `compute.unknown-column`. A column called `and` or `or` is an ordinary column in an operand position. `@N` takes its digits right after the `@` (`/ a:int @2`, never `@ 2`), as before.

**K7b1 in detail (choice).**

* **Operators**: `= != < <= > >=`, **bytewise** (no collation, no locale; `"B" < "a"` is true; the shorter text is the lesser when one is a prefix of the other). Both sides are texts: a number against a text is `compute.type-mismatch` (the K6 rule, no conversion), as is a typed column on either side of a text comparison, and a text literal beside a number operator.
* **The syntax**: `name = "x"`, `"x" != name`, `a < b` for two untyped columns. A bare word in the operand position of a comparison reads as a column without a type (as in K6); to tell a text comparison from a number one, the compiler reads the first operand: a typed column or a number starts a number comparison, an untyped word or a string literal starts a text one, and the second must be of the same kind. *The spacing rule of K7a stands and gets one more clause:* a comparison operator after an **untyped** column needs a space before it when the column's name could contain `<`, `>` or `!`, because those do not end a bare word (**read**: `stops_word` in `cexpr.cho`); the refusal is `compute.unknown-column`, and the repair says to put a space. `=` already ends a word.
* **The program**: two operand loads and one comparison, `op_tld` (a column or a literal: the `a` and `b` of an `op_lit`) twice and `op_tcmp` with the operator, the verdict then jumping as in K7a. The loads hold the two ranges in the evaluator's own variables, not in the number slots. Evaluation stays lazy: a text comparison that is not reached reads no cell (a text cell cannot fail, so this is only an economy; **no new refusal** and no new rule).
* **The explain** counts the instructions and adds nothing to the rules (a text cell cannot be refused).

**K7b2 in detail (choice), corrected before it was built (2026-11-16).** *The first version of this paragraph put the `if` in the text evaluator and let an arm be any text. Reading the code for the build showed that cannot be: the condition of an `if` may compare numbers (`if(qty > 0, "in stock", "sold out")` is the case that matters), the exact number machine (`cmpv`, `cexpr.eval`) is where those comparisons run, and the text evaluator (`ctext.eval`) has no number workspace; and the parser of a number expression (`define`) is the one that reads a condition. So the text `if` is read by the number parser and run by the number machine, and what it can hold in an arm shrinks to what needs no other machine.* `if(cond, a, b)` is a text when both arms are **leaf texts**: a column with no type, a string literal, or another such `if`. The machine selects a leaf and the row writes it as a quoted cell (the doubled quotes of a quoted cell and of a literal carried over, a quote of an unquoted cell doubled), so it adds no refusal: a leaf cannot fail, and `compute.result-too-long` stands for the written cell. ### 3.5 K8: dates (design 2026-11-15; K8a and K8b built 2026-11-16)

> **Status: K8a, the five functions that give a number, and K8b, `add_days`, which gives a text, are built (the as-built blocks at the end of this section).** **The maintainer's go for K7 then K8 (2026-11-15, "go with k7 then k8") is read as the confirmation that open question 1 asked for: day-count arithmetic on `:date`.** It reopens the non-goal "no arithmetic" of `docs/datetime.md` section 15 for **days only**, and that sentence now points here. If the reading is wrong, K8 stops at this document.

**Read.** A `:date` cell is `YYYY-MM-DD` and nothing else, read as a count of days since 1970-01-01 (`dtparse.parse(data, 22)`; `docs/datetime.md` section 4.1); `dtparse.put(heap, out, v, 22)` writes one back; the civil calendar is `days_from_civil` / `civil_from_shifted` (`tools/table/dtparse.cho`). A cell that is not a date is refused by the reader with the rule `value.not-date` family as today. K8 adds no parser and no calendar.

| function | arguments | result | meaning |
|---|---|---|---|
| `year(d)` | a column `NAME:date` | number, scale 0 | the year, 1 to 9999 |
| `month(d)` | the same | number | 1 to 12 |
| `day(d)` | the same | number | 1 to 31 |
| `weekday(d)` | the same | number | **ISO: Monday is 1, Sunday is 7** (choice; 1970-01-01 was a Thursday, 4) |
| `days_between(a, b)` | two `:date` columns or date literals | number (signed) | `b - a` in days: `days_between(due, paid)` is positive when paid is later |
| `add_days(d, n)` | a `:date` column or literal, an integer literal or an integer column `n:int` | **a date, written as text** `YYYY-MM-DD` | the date `n` days after (negative: before). A result outside 0001-01-01 to 9999-12-31 is `compute.date-out-of-range` for that row, never wrapped |

A date literal is `"YYYY-MM-DD"` in double quotes (the string literal of K6), validated at compile time by the date parser (an invalid one is `compute.bad-literal`). The number results are **leaves** of the exact machine (as `len` is): `year(d) * 100 + month(d)` and `if(days_between(a, b) > 30, ...)` are expressions of K5 and K7. `add_days` is **text-valued** with kind date: it is written as a quoted cell like any text of K6, and it can feed `concat`, `substr` and `len`, but not be compared as a date (compare with `days_between`; **choice**, so there is no date kind in the machine). A date result is never a column the stage then reads as `:date` again; the user types it on the next stage.

**New refusals.** `compute.date-out-of-range` (row, exit 8). A cell that is not a date is the existing date refusal of the reader (its rule, not a new one). `compute.type-mismatch` for a non-date argument (a column with another type, a text) and `compute.arity`.

**Stays out.** `strftime` and formatting other than `YYYY-MM-DD`; timestamps and datetimes (`:timestamp`, `:datetime` take no function in K8: a day count of an instant is a zone question); zones, `now`, epoch integers, leap seconds, week numbers, month arithmetic (`add_months`: the end-of-month rule is a policy), business days.

**Gates.** **G-DT-ORACLE:** `scripts/cdate_ref.py` uses Python's `datetime.date` (no code shared with the tool): **every date from 0001-01-01 to 9999-12-31 for `year`, `month`, `day`, `weekday`** (3,652,059 days, one run), random pairs for `days_between`, random `(date, n)` for `add_days` including the two ends and the leap days of 1900, 2000, 2100, and a refusal check outside the range. **G-DT-MUT:** the epoch constant, ISO weekday as Sunday 0, `is_leap` of a century, the sign of `days_between`, `add_days` off by one at the range end, a month of 31 days for April. **G-DT-WRITE:** the output of `add_days` through CSV, JSON and JSON lines. The surface gates of section 5.

**Not claimed.** No cost; no claim about `:timestamp`.

**K8a as built (2026-11-16).** `year`, `month`, `day`, `weekday` (ISO, Monday is 1) and `days_between(a, b)` (`b - a`, signed) are built as designed; **`add_days` is not** (it gives a text, so it needs the text evaluator of K6 to read a date operand: it is K8b, and a call of it is `compute.unknown-function` until then). *Corrected in place:* the design said `add_days` takes `n:int` or an integer literal; that waits for K8b.

* **The program.** One new instruction, `op_dt`, a leaf of the exact machine like `len`: `a` is the function plus 32 when the first operand is a literal and 64 when the second is, `b` and `c` the operands (a column, or the days since 1970-01-01 of a literal). The code is `tools/table/cdate.cho` (the calendar is `dtparse`'s, `civil_from_shifted`; the weekday is `(days + 3) mod 7 + 1`, 1970-01-01 being a Thursday); the parser of the arguments, `date_at`, is in `cexpr.cho`. A cell is read as a date only when the instruction runs, so the arm of an `if` that is not taken never reads it.
* **The syntax.** An operand is `NAME:date` (or `#N:date`) or a date literal `"YYYY-MM-DD"` in double quotes, checked at compile time against the real calendar. The result is a number of scale 0, so `year(d:date)*100+month(d:date)`, `days_between(a:date, b:date)/7@2` and `if(days_between(a:date, "2026-01-01") > 30, ...)` are expressions of K5 and K7a. Other statuses: 14 (wrong number of arguments), 15 (a literal that is not a real date), 16 (an operand that is not a date: another type, no type, a number, an earlier definition), 2 (the column is not there).
* **A cell that is not a date** is refused with the reader's own rule, `value.not-date`, with `detail.reason` and `detail.offset` as in `--where` (`dtparse.tag_of`, `dtfail.message_of`), the context `compute`, the column, the row and the line, and no payload; the hint is the one of `--compute` (an earlier call). The explain lists `value.not-date` for a definition that reads a date and for no other. **No new rule was needed.**
* **A refactor the limit forced.** `cexpr.cho` came to 1,999 lines with the date parser, one under the limit of 2,000. The readers that look only at the text of a definition (`number_at`, `scale_literal`, `default_literal`, `type_at`, `string_at`, `digits_at`) moved to `tools/table/clit.cho`, unchanged: `cexpr.cho` is 1,852 lines. Four older mutants name their module now.
* **Gates, as run** (compiler `119bcfe`, 16 Nov 2026).
  * *G-DT-ORACLE.* **Every date from 0001-01-01 to 9999-12-31** (3,652,059 of them) through `year`, `month`, `day` and `weekday` in one run of the binary, against Python's `datetime.date`: 0 differences (`tests/conformance/test_compute_date.py`); `days_between` over 20,000 random pairs, the two ends and the epoch: 0 differences; and in `scripts/cexpr_golden.py` the same reference over the probe, **7,783 cases at each of three seeds, 0 differences** (1,200 random date definitions, with bad cells, inside operators, functions and `if`; the hand cases are facts: 1970-01-01 a Thursday, 0001-01-01 a Monday, 9999-12-31 a Friday, 2000-02-29 a Tuesday, 11,016 days from the epoch to it, 3,652,058 from the first date to the last, and the days of the century years 1900, 2000 and 2100).
  * *G-DT-MUT.* 18 mutants of the date code (the epoch constant, the first day of the week, Sunday as 0, no positive modulus before 1970, the sign, the flag of the second operand, a literal read as a column, year as month, an invalid literal accepted, any type accepted, a status with no reason, no push, the leaf's scale, the two arities, a number as a column name, an earlier definition, the second literal's flag) on top of the 85: **103 of 103 killed**, in a run with nothing else touching the sources.
  * *G-DT-WRITE.* Not applicable to K8a: the result is a number.
* **Found by the gates:** two of my hand cases were wrong and the tool right (a definition named `d` is a column's name, `compute.duplicate-name`; and the days between 2026-11-16 and 1970-01-01 are 20,773, not 20,408), and one expected value of a test (`9757 / 7` is `1393.86`).
* **Not measured:** the cost of a date function; no speed is claimed.

**K8b as built (2026-11-16): `add_days(d, n)`.** The date is `NAME:date` or a date literal in double quotes; the count is an integer literal (digits, with a minus sign first if it is negative: at most nine digits) or a column `NAME:int`. It is a **text** (the date written `YYYY-MM-DD`, a quoted cell like every text of K6), so a definition may be `add_days(...)` alone or any text function around it (`concat(add_days(d:date, 30), " due")`, `substr(add_days(d:date, 1), 1, 4)`), and in a number it is `compute.type-mismatch` (`add_days(...)+1`, `len(add_days(...))`: `len` takes a column or a literal, as K6 chose). *Corrected in place:* K8a's line saying a call of `add_days` was `compute.unknown-function` until then is now `compute.type-mismatch` in a number and a value in a text.

* **The program.** One more leaf of the text evaluator (`ctext.op_add_days`, 26): `a` is 26 plus 32 when the date is a literal and 64 when the count is, `b` the date column or its days, `c` the count column or the count. The date and the count are read when the instruction runs; the sum is written into the arena by `dtparse.put`. The parser of the arguments is `date_at` (the same as the date functions) with `days_at` for the count. `cexpr.cho` is 1,943 lines.

The first rule of K8 that is new; its registry entry, the explain and the fixture of `test_rules` are in. ## 4. Rules (every refusal has a tag)

New: `compute.unknown-function` (the name, the table of names in `detail`) · `compute.arity` · `compute.type-mismatch` (the argument, the kind it wanted and the kind it got) · `compute.result-too-long` · `compute.not-utf8-boundary` (K6) · `compute.bad-literal` (a scale outside 0..18, a negative count) · K7: `compute.mixed-and-or`, `compute.too-many-conditions` · K8: `compute.date-out-of-range`. Existing `compute.*` and `value.*` unchanged. **No payload in any message.**

## 5. Gates (written before the code, each able to fail)

* **G-FN-ORACLE.** For each function, `tests/conformance/compute_fn_ref.py` (Python, sharing no code with the tool) generates random definitions over random typed tables, with hostile cells (the empty cell, NUL, `"`, `\`, U+2028, a 4-byte character, a half character, digits past the scale, 18-digit numbers, ties of half-even for every sign) and compares **stdout, stderr and the exit status**, refusals included.
* **G-FN-MUT.** `scripts/compute_fn_mutants.py`: per function, mutants the oracle must kill (half-even to half-up, `trim` of one side only, a cut inside a character allowed, an off-by-one `substr`, `lower` of a non-letter, `coalesce` of a non-empty bad cell, the result bound off by one, an argument swapped). A survivor is explained or the gate is extended.
* **G-COMPAT.** The corpus md5 of `scripts/corpus.py` and the instruction counts of the select loops (callgrind, budget 1.01) equal those of `main`: no byte of the existing paths changes (`docs/computed-columns.md` section 7).
* **G-FLAT.** Peak resident memory of one definition of each function class is flat in the rows (the repository's `maxrss` launcher), as `test_compute.test_memory_is_flat_in_the_rows` holds for the arithmetic.
* **G-COST.** Per function, wall time per row on the repository's 1,000,000-row file, next to the numbers of the stage as it is. **No speed is claimed before this table exists.** Baseline, **measured** (`docs/computed-columns.md` section 7, 4-core container): `--select id,price,qty` 93 ns a row; `--compute 't=price:dec(2)*qty:int'` 279 ns; a product and a division 555 ns.
* **G-EXPLAIN.** The explain of a stage lists exactly the definitions that run, with their kinds; a corpus of stages is run with and without `--explain`, and every refusal that the explain calls certain is the one the run gives.
* **G-SURFACE.** `introspect`, `skill`, the MCP schema and AGENTS.md are regenerated from the signature table, and every example in them is run.
* **G-NOPANIC.** A fuzz of function names, arities, literals and cell bytes: no input reaches a panic.

## 6. What stays out

In-place rewrites (`--lower COL`, `--clip`, `--sentinel`, `--dedupe`); a function in `--where`, `--query`, `--group`, `--agg`, `--join` or `--order-by`; `:float` operands and float functions (`sqrt`, `exp`: a double is rounded by every operation, `docs/computed-columns.md` section 3.1); regular expressions; user-defined functions; locale, `now`, zones, `strftime`; Unicode case mapping.

## 7. Open

1. **Dates (K8):** day-count arithmetic only, no zones: read as confirmed by the maintainer's "go with k7 then k8" (2026-11-15); if that reading is wrong, section 3.5 stops being a plan.
2. **`text(x)`**: a number written as text, exact at its scale. Needed by `concat(name, '-', id)`; without it `concat` takes texts only and a number column is not a text operand.
3. **Unicode case mapping** and a **character-count `len`**: out for v1; the names are not taken (`upper`, `lower` and `len` are the ASCII and byte ones, and say so).
4. **K7:** K7a is built as designed. **K7b** (section 3.4) is designed in two slices, K7b1 (a column or a literal in a text comparison) then K7b2 (a text `if`), as a recommendation, to confirm; a call as a comparison operand, `text(x)` and a date comparison stay open.
5. **Window functions** are a different stage (a materialising one) and have their own document.
