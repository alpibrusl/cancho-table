Evidence

What has been tested and how, what was measured and on what, and the cells where table loses. Every number is copied from the document it names, with its conditions; the counts below are computed from the repository.

What has been tested, and how

The conformance tests run against the built binary (tests/conformance). CI builds the pinned compiler and runs the formatting check, the build, the schema and authority checks, these tests, and a smoke run of the benchmark script. The mutant scripts are not run in CI: each is one build and a test run per mutant.

Differential, against Python

  • The shape and --select against Python’s csv module in strict mode: hand-picked fixtures (quoted LF and CRLF newlines, a BOM, empty fields, doubled quotes, a header only, an empty file, an unterminated quote, ragged rows, text after a closing quote).
  • Thousands of random tables written by csv.writer and then damaged, and fields that straddle the 64 KiB chunk boundary. A selection must equal Python’s fields, and its CSV must be the bytes csv.writer writes.
  • Every benchmark answer is checked against one computed in Python before it is timed; a contender that disagrees stops the run.

Against itself

  • --threads N must give the sequential bytes: every plan with N in 2, 3, 4, 8, 16 and ranges of 1, 7, 64 and 1000 bytes (a boundary inside almost every record), 350 generated tables, the same run 200 times, 300 fuzz inputs, sums at the edge of 64 bits in every order that matters (docs/parallel.md section 4).
  • scripts/corpus.py: the md5, status and error of 134 plans over the benchmark and adversarial files, sequentially and with threads and tiny ranges, the same 134 lines before and after every cell-cost round.

Rules, memory, authority

  • Every rule the tool declares has a fixture that reaches it, with its exit code and, for a retry repair, a re-run that succeeds.
  • Peak resident set is flat on a 2 MB and a 37 MB file for each way of reading, and on a record of 20 MB over 200,000 lines. No input reaches a trap (fuzz).
  • The binary’s authority report is the committed one, within tools.toml; under strace (Linux) there is no socket and no write on disk.

What the mutants found, and what is stale

  • The cell-cost mutants (cellcost_mutants.py) were all killed on the Linux box, and three equivalent ones are said so in the script. The first run had seven survivors, five of them real: the tests checked a refusal’s status and not its rule, did not hold a group in the cache before a collision, and so on. The tests were sharpened and all seven killed (docs/history.md, “Tests and mutants”).
  • A mutant that removed a test found a real bug in --threads: a page that fills at the last good row of a range was taken whole, with the ragged rows that follow it counted. It led to a test that failed, and a fix. A mutant that moved a range’s end one byte early did not change an answer: it hung, and a loop that was only shown to end by a proof now also has a guard.
  • Stale: select_mutants.py and filter_mutants.py point at code that moved to engine.ls and scan.ls; 21 of their sites no longer match, they stop at their first check, and they have not run since. That is in docs/backlog.md. The two other lists are current. The counts in the table are the scripts’ own; two sentences in the docs that quoted other numbers were corrected.

Benchmarks: the method, and the standard file

The file is the design’s: 1,000,000 rows of id,status,bytes,path,note, the last quoted, seeded, 31,667,311 bytes (scripts/bench.py). Minimum of 5 interleaved runs, output to /dev/null, peak resident set from /usr/bin/time on one more run. Before any timing every contender’s answer is parsed and compared with one computed independently in Python. Contenders: csvtk 0.38.0 (-j 1 unless said), Miller 6.22.0 (Linux only), DuckDB 1.5.6 (Mac only; COPY (...) TO '/dev/null' over read_csv with type detection), and awk and cut|sort|uniq -c as floors that are not CSV-aware.

What these numbers are not: a claim about every question. Everything here is one file, two integer columns and one low-cardinality group column; table does less than the incumbents (no types, one sort key, integers only: csvtk summary computes floats and Miller is a whole language). The awk and uniq rows are floors where CSV quoting does not matter and are not equivalent on the quoted column; the uniq pipeline is three processes running in parallel on the Linux box’s other cores, which is why it matches table there. The Linux box’s load differs from run to run, which is why its absolute times differ between rounds more than the ratios do.

The adversarial round: where does table lose?

Registered before any of it was run: the first commit of docs/adversarial.md is the registration, with the cells, the incumbents, how each is run and the predictions; the results came in later commits. A loss is table’s time above an incumbent’s at the same thread count, or at the machine’s thread count above the incumbent’s default; a material loss is a ratio above 1.25; a memory loss is a peak above 4x the incumbent’s and above 64 MB; a cliff is time per megabyte rising more than 3x from the benchmark file’s. Nothing is tuned to avoid a loss and no cell is dropped because it is bad. Not run: many small files, joins, sorts of non-key columns, Parquet (not features).

The Linux box’s load changes by the hour, so the base column is the thing to compare with, not the first round’s numbers. I1 is the one slowdown that was real (+6 to +8 percent on the Mac): the way a distinct aggregate is decided cost a call and two loops per row; round 15 of docs/history.md decides it once (0.293 s on main, 0.268 s now, Mac), and these tables were measured before it.

What the round did not change

  • A million keys, or distinct over a unique column: a 3x to 3.4x loss to DuckDB at one thread and 9x at its default. Each row creates a group and nothing in the round touches that cost (the groups are moved by value, the key is hashed twice). --threads does not help (B3 at t8 0.790 against t1 0.792): the serial merge. The backlog says to not use --threads for a high-cardinality grouping.
  • Long fields do not scale with threads, and the cause was checked: the same file without newlines inside the quoted fields goes from 0.017 s to 0.0086 s at eight threads; with a newline every 17 bytes, 0.172 s and 0.170 s.
  • The sort. There is no row sort. The proxy is not the same question.
  • Memory is the same: a few MB for a scan, 135 to 180 MB for a million groups. Against it, csvtk’s summary used 11.8 to 14.8 GB on the 100,000 and 1,000,000-key sums and was killed on Linux; Miller used 0.5 to 3.9 GB. No cliff by the registered definition (the longest, E1, was at 0.93x).

Claims corrected in place

  • The first DuckDB comparison compared only the group-count answers; the later tables check every contender’s answer first, and the document says so.
  • The cell-cost plan blamed four memchrs per cell in csv_value; the profile showed that was the output side, and the larger costs were moving the group state in and out of a call for every row (the filter’s time per row went from 50 to 43 ns, the group-count’s from 110 to 52). The backlog item is struck through, with the reason.
  • The first pass at the grouping regressed the cut from 0.057 s to 0.093 s in code that had not changed. It was found only because the old benchmark was kept in the loop.

Reproduce

Build build/table as the overview does, then, from the repository root:

python3 scripts/bench.py                 # the 1,000,000-row file, every contender's answer checked, then timed
python3 scripts/bench.py --rows 20000 --runs 1    # the smoke run CI does
python3 scripts/bench_parallel.py        # the thread curve; --threshold for where threads start to pay
python3 scripts/adversarial.py           # the 16 cells; --cells B1,B3 --runs 5 --threads 8; --base OLD_BINARY compares two builds
python3 scripts/corpus.py                # the md5 of 134 plans, to compare before and after a change (needs the files the two scripts above generate)
python3 -W ignore -m unittest discover -s tests/conformance -v
python3 scripts/parallel_mutants.py      # also select_, filter_ (stale) and cellcost_mutants.py

csvtk, Miller and DuckDB are used where they are installed; a contender that is missing is skipped, and one whose answer disagrees is reported and not timed. Files are generated under build/ and never committed.

What this evidence does not show

  • One file shape for the headline numbers, two machines, and the sixteen adversarial cells; not every file and not every question.
  • The Linux box was loaded (a soak was running) for every Linux number, and DuckDB was never run there.
  • Causes on Linux are by timing experiment or inference, because perf is not permitted there; the Mac causes are from a profile (sample).
  • The tests compare with Python’s csv; a file on which Python’s reader and this one are meant to differ (a lone CR is a byte of a field here, a record break there) is documented, not hidden.
